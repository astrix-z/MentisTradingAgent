## 2. Решения владельца

| D | Вопрос | Решение |
|---|---|---|
| D1 | Набор T6 (H1/M15/M5 = 12:3:1) нарушает текущее правило `tide:wave:ripple = 16:4:1` | **Остаётся только порядок:** `tide > wave > ripple` (строго, в мс). Кратность не требуется |
| D2 | Имя второго набора | **`Fast`** |
| D3 | Что значит «список задаётся/корректируется в отдельном блоке» | **Свободное редактирование:** в список можно вписать любое значение. Если агент его не поддерживает, UI предупреждает при сохранении списка, и Start с таким значением блокируется (§4.5) |

## 3. Что есть сейчас

- Параметры описывает только агент: `agent/agent/strategies/tripple_screen/settings.py`
  (`TripleScreenSettings`, pydantic, frozen). Межполевые правила продублированы как
  данные в `.../tripple_screen/schema.py` (`CONSTRAINTS`, `LOOKUPS`) и публикуются в
  Redis-каталоге `agent:strategies` (`agent/agent/protocol.py`).
- Backend валидирует Start по опубликованному каталогу
  (`backend/app/core/strategy_catalog.py`, `trading.py:_enforce_strategy_params`) и
  отдаёт каталог UI через `GET /trading/strategies/`. Параметры в БД backend не хранятся:
  последние параметры запуска лежат только в Redis-снапшоте `desired`.
- UI (`frontend/src/routes/_layout/strategy.tsx` + `components/strategy-form/strategySchema.ts`)
  строит форму по JSON Schema. Поле с `enum` отображается как **свободный `<Input>` с
  `<datalist>`**, то есть ввести можно что угодно. `validateSettings` вызывается
  **только при нажатии Start** (`strategy.tsx:270`). Форма заполняется из `status.desired.params`.
- Интервалы: `interval_ms` принимает только `s/m/h` (`settings.py:23`), так что D1 и W1
  сейчас недопустимы. В `agent/agent/execution/monitor.py:73` есть своя копия, которая
  знает `d`. Границы баров везде считаются как `ts // step * step`
  (`strategy.py:380, 416, 552`, `monitor.py:190, 276`). Для D1 это верно (UTC-полночь),
  **для W1 нет**: недельная свеча Binance открывается в понедельник 00:00 UTC, а эпоха
  начинается с четверга.
- Правило 16:4:1 записано в `settings.py:117` и `schema.py` (`RATIO_MESSAGE`).
- Поля `swing_low_h1_n` / `trail_m15_n` используются в `strategy.py:734, 806`, `schema.py:130`,
  тестах агента, `frontend/tests/fixtures/strategy-catalog.json` и `docs/STRATEGY_TRIPPLE_SCREEN.md`.
  В БД backend (`swing_low_ref`) их нет.

## 4. Решение

### 4.1 Агент: поля, интервалы, правило таймфреймов

1. **Переименование (T2a).** `swing_low_h1_n` → `swing_low_wave_n` (title `Swing low WAVE N`),
   `trail_m15_n` → `trail_ripple_n` (title `Trail RIPPLE N`). Старые ключи принимаются через
   `validation_alias=AliasChoices(new, old)`: без этого агент, перезапущенный со старым
   снапшотом `desired`, молча взял бы дефолт, потому что `from_params` отбрасывает
   неизвестные ключи. В опубликованной схеме остаются только новые имена
   (`additionalProperties: false` не меняется).
2. **D1 и W1.** Одна общая функция в `agent/agent/common/` (или рядом):
   `interval_ms(interval)` и `bar_open(ts, interval)` с учётом смещения недели
   (`1w`: выравнивание на понедельник 00:00 UTC). Все места с `ts // step * step`
   переходят на неё, и копия в `monitor.py` удаляется. `1M` (календарный месяц) не
   поддерживается и из лукапа исключён явно.
3. **Правило таймфреймов (D1).** В `coherent()` и в `CONSTRAINTS` правило 16:4:1 заменяется
   на `intervals_ms[tide] > intervals_ms[wave]` и `intervals_ms[wave] > intervals_ms[ripple]`
   (`cmp: gt`, новая грамматика не нужна). Сообщение:
   `"timeframes must satisfy tide > wave > ripple"`.
4. **Аудит стратегии под некратные ТФ.** `_snapshot` берёт волну с cutoff = `trigger.open_time`,
   а прилив и рябь с cutoff = `trigger.close_time`. При некратных парах (H6/H4) это по-прежнему
   «последний полностью закрытый бар». Нужен тест, который это доказывает (§7).
5. **Опубликованные интервалы.** `LOOKUPS["intervals_ms"]` — всё, что агент реально умеет
   (теперь с `1d`, `1w`). Это «множество поддерживаемых» (S), отдельное от UI-списков (§4.3).

### 4.2 Захардкоженные наборы (T5, T6)

- Файл `agent/agent/strategies/tripple_screen/presets.py`: `BUILTIN_PRESETS = {"Default": {...}, "Fast": {...}}`
  в виде явных словарей (значения в §5).
- Тест: `Default` совпадает с дефолтами `TripleScreenSettings()`, а каждый набор проходит
  `TripleScreenSettings.model_validate` и опубликованные `CONSTRAINTS`.
- Наборы публикуются в каталоге рядом с `settings_schema`: `"presets": [{"name", "params"}]`.
  Поле необязательное, `CATALOG_VERSION` остаётся 1: `CompiledCatalog` сравнивает версию
  на строгое равенство (`strategy_catalog.py:478`), и при версии 2 backend, выкаченный
  раньше агента, отверг бы каталог целиком, то есть и Start. Backend читает
  отсутствующее поле как `[]`, а набор, не прошедший проверку схемой, логирует и пропускает.
- Почему в агенте: он единственный владелец параметров (принцип `protocol.py`). Отдельная
  копия в backend-миграции устарела бы при первом же изменении дефолтов.

### 4.3 Backend: БД и API

Новые таблицы (Alembic-миграция backend, `backend/app/alembic/versions/`):

```
strategy_preset
  id            uuid pk
  strategy      varchar(64)          -- "tripple_screen"
  name          varchar(64)          -- уникально по (strategy, lower(name))
  params        jsonb
  is_builtin    bool                 -- Default/Fast: только чтение
  created_by    uuid fk user null
  created_at, updated_at  timestamptz

strategy_field_options
  strategy      varchar(64)
  field         varchar(64)          -- quote_asset / tide_interval / wave_interval / ripple_interval
  options       jsonb                -- упорядоченный список строк (коды Binance: "4h", "1d", "1w")
  updated_at    timestamptz
  pk (strategy, field)
```

- **Встроенные наборы в БД.** При чтении каталога backend делает upsert `Default`/`Fast` с
  `is_builtin=true` (идемпотентно, код важнее БД). Имена `Default` и `Fast` зарезервированы
  без учёта регистра. PUT и DELETE для встроенных наборов возвращают `409`.
- **Начальные списки** заполняет миграция значениями из T2 (коды Binance; `W1` = `1w`).
- **API** (только superuser, префикс `/trading/strategies/{strategy}/`):
  - `GET presets/` возвращает наборы, у каждого `valid` и `errors`, пересчитанные по текущему
    каталогу и спискам. Набор может перестать быть валидным после изменения агента или списков.
  - `POST presets/`, `PUT presets/{id}`, `DELETE presets/{id}`. При сохранении работает та же
    проверка, что на Start (схема + `CONSTRAINTS` + списки). Если каталога нет, сохранение
    отклоняется с `503`, как и Start. Имя: 1–64 символа после trim, уникально.
  - `GET options/` возвращает `{field: {options, unsupported: [...]}}`, где
    `unsupported = options − S`.
  - `PUT options/{field}` принимает любые непустые строки без дубликатов (D3). В ответе
    `unsupported` для предупреждения в UI. Пустой список запрещён (`422`).
- **Start (T1).** `_enforce_strategy_params` дополнительно проверяет, что каждое поле со
  списком входит в `options ∩ S`. Ошибка приходит в формате pydantic-`loc`, как остальные.
  Если списков в БД нет, действует только S.

### 4.4 Отображение интервалов

В БД и API хранятся коды Binance (`1w`, `1d`, `12h`, …, `1m`). UI показывает их как
`W1, D1, H12, …, M1`, и в редакторе списков можно вводить любую из двух записей:
двусторонняя функция `intervalLabel/parseInterval` в `strategySchema.ts`. Ввод, который не
разбирается ни в одну форму, помечается ошибкой поля и не сохраняется.
Порядок опций задаётся списком из БД (от старшего ТФ к младшему, как в T2).

### 4.5 Frontend

1. **Выбор набора (T3)** — `Select` над полями: встроенные наборы идут первыми и помечены
   `built-in`. При выборе заполняются все поля. Если после этого поле изменить, в
   селекторе показывается `<имя> (изменён)`. Кнопки: **Save as…** (диалог с именем),
   **Update** (только для своих наборов), **Delete** (с подтверждением, только для своих).
   Невалидный набор можно выбрать, но его ошибки сразу видны у полей.
   Начальное состояние: если параметры из `status.desired` совпадают с каким-то набором,
   выбран он; иначе показывается `— текущие параметры запуска —`. Если снапшота нет,
   выбран `Default`.
2. **Поля со списком (T2)** — настоящий `Select` вместо `Input + datalist`. Опции берутся
   из списка БД. Опция вне S видна, но неактивна (disabled) с подсказкой «агент не
   поддерживает». Значение, которого нет в списке (например, из старого набора), показывается
   с ошибкой поля.
3. **Живая валидация (T1)** — `validateSettings` вызывается на каждое изменение
   (дебаунс ~200 мс), ошибки выводятся под полями, а Start и Save недоступны, пока ошибки есть.
   Backend проверяет повторно и остаётся последним рубежом.
4. **EMA tide periods** — три числовых поля a / b / c вместо текста через запятую.
   Правило a < b < c уже опубликовано (`CONSTRAINTS`), новое только в отображении.
5. **Блок «Списки выбора» (T2)** — отдельная карточка на той же странице, свёрнута по
   умолчанию. Для каждого из четырёх полей: чипы значений, поле «добавить», удаление и
   перестановка, кнопка Save. Значения вне S подсвечены предупреждением (D3). Удаление
   значения, которое используется в сохранённом наборе, разрешено, но набор после этого
   становится `valid=false`, и UI об этом предупреждает.

### 7.1 Приёмка

- Агент: `Default == TripleScreenSettings()`; `Fast` валиден; старые ключи
  `swing_low_h1_n`/`trail_m15_n` дают те же значения; `bar_open` для `1w` возвращает
  понедельник 00:00 UTC (проверено на реальной строке klines Binance); прогон стратегии на
  паре H6/H4/H1 выдаёт только закрытые бары; `test_strategy_catalog.py` подтверждает, что
  `CONSTRAINTS` и модель отклоняют одни и те же наборы, включая `tide ≤ wave`.
- Backend: CRUD наборов; `409` на изменение встроенного; `422` при сохранении невалидного
  набора; Start со значением вне списка → `422` с `loc`; список со значением вне S
  сохраняется, но Start с этим значением → `422`; без каталога сохранение → `503`.
- UI (Playwright): выбор `Fast` заполняет все 22 поля; правка поля → `Fast (изменён)`;
  Save as → набор появляется после перезагрузки; невалидное значение блокирует Start до
  исправления; удаление `M5` из списка ripple делает `Fast` невалидным и показывает это в
  селекторе; W1 и D1 доступны в прилив (tide).
- Проверки из `development.md` (ruff, strict mypy для backend и агента, biome, `tsc`,
  pytest, Playwright) — зелёные.

## 8. Риски и открытые вопросы

- **R-a. W1/D1 при `kline_window = 1000`.** Нужна история в 1000 недель (~19 лет) или
  1000 дней (~2,7 года). Отбор пропускает символы с короткой историей, поэтому W1 при таком
  окне фактически не торгует ничего, а D1 торгует только старые листинги. Валидация этого
  не ловит: это данные, а не параметры. Предложение: в UI **показывать предупреждение, но не
  блокировать**, если `tide × kline_window` больше ~3 лет. Нужно подтверждение владельца.
- **R-b. Некратные таймфреймы (D1).** Разрешены пары вроде H6/H4, где закрытия баров не
  совпадают. Корректность `_snapshot` покрывается тестом (PRESET-03), но смысл сигнала на
  таких парах не проверялся на истории.
- **R-c. Дрейф схемы.** Если агент добавит поле, в старых наборах его не будет. `GET
  presets/` вернёт `valid=false`, а UI при выборе подставит дефолт из схемы и покажет
  `(изменён)`. Молча ничего не заполняется.
- **R-d. Свободные списки (D3).** В список можно внести значение, которое агент не
  поддерживает. Защита — предупреждение при сохранении, disabled-опция и `422` на Start.
- **Не цели v1:** наборы для execution-настроек; имя набора в Start-снапшоте и Status;
  история изменений наборов; права доступа к наборам по пользователям (все superuser видят
  все наборы).

## 9. Обсуждение

Правила те же, что в `docs/ORDER_EXECUTION_PLAN.md` §14. Документ — единственный источник
правды. Ревьюер не правит §1–§8, а добавляет треды ниже:

```
### R<n> [<раздел, напр. §4.3>] <короткий заголовок> — <автор>, <дата>
**Предложение:** что поменять/добавить.
**Почему:** аргументы, ссылки на код/доки/SDK.
**Статус:** open
```

Ответы — в том же треде строками `**<автор>, <дата>:** ...`. Итог:
`**Статус:** accepted (внесено в vN) | rejected (причина) | needs-owner (→ D<n>)`.
В ClickUp только уведомления («добавлены треды R1–R3», «план v2»).
