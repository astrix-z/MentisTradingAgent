## 3. Что есть сейчас

- Параметры описывает только агент: `agent/agent/strategies/tripple_screen/settings.py`

  данные в `.../tripple_screen/schema.py` (`CONSTRAINTS`, `LOOKUPS`) и публикуются в
  Redis-каталоге `agent:strategies` (`agent/agent/protocol.py`).
- `TripleScreenSettings.from_params` (`settings.py:137–142`) **отбрасывает ключи, которых нет
  в `model_fields`, до валидации**. Через него идут конструктор стратегии
  (`strategy.py:50–55`), команды (`common/commands.py:290–313`) и восстановление
  (`common/commands.py:530–572`, `engine.py:212`).
- Backend валидирует Start по опубликованному каталогу
  (`backend/app/core/strategy_catalog.py`, `trading.py:_enforce_strategy_params`, общий для
  обоих Start-маршрутов) и отдаёт каталог UI через `GET /trading/strategies/`. Компилятор
  подставляет дефолты только для `CONSTRAINTS`, наружу отправляется исходный payload
  (`trading.py:598–605`). Параметры в БД backend не хранятся: они есть в потоке команд
  (`trading.py:579–588`) и в Redis runtime-снапшоте (`desired`, `engine.py:54`).
  Каталог кешируется в памяти процесса (`strategy_catalog.py:518–561`), воркеров четыре
  (`backend/Dockerfile:69`).
- UI (`frontend/src/routes/_layout/strategy.tsx` + `components/strategy-form/strategySchema.ts`)
  строит форму по JSON Schema. Поле с `enum` отображается как **свободный `<Input>` с
  `<datalist>`**. `validateSettings` вызывается **только при нажатии Start**

- Интервалы: `interval_ms` принимает только `s/m/h` (`settings.py:23–34`), так что D1 и W1
  сейчас недопустимы. В `execution/monitor.py:73` есть своя копия с `d`; монитор вычитает

- Правило 16:4:1 записано в `settings.py:113–118` и `schema.py:70–93` (`RATIO_MESSAGE`).
- Поля `swing_low_h1_n` / `trail_m15_n` используются в `strategy.py:734, 806`, `schema.py:130`,

## 4. Решение

### 4.1 Агент: поля, интервалы, правило таймфреймов

1. **Переименование (T2a).** `swing_low_h1_n` → `swing_low_wave_n` (title `Swing low WAVE N`),
   `trail_m15_n` → `trail_ripple_n` (title `Trail RIPPLE N`). Старые имена переводит
   `model_validator(mode="before")` по таблице `LEGACY_KEYS = {old: new}`, а
   `from_params` пропускает ключи из `model_fields ∪ LEGACY_KEYS`. Так миграция работает на
   всех путях: `model_validate`, `from_params`, конструктор, восстановление `desired`,
   доставка ранее поставленного Start. Правило: только старое имя → значение переносится
   (и валидируется, `0` — ошибка, не дефолт); оба имени есть → каждое значение валидируется
   типом поля, равенство сравнивается **после** валидации (`"7"` и `7` равны): равные
   валидные → берётся новое, любое невалидное → ошибка поля, разные → `ValueError`. В опубликованной схеме только новые имена
   (`additionalProperties: false` не меняется). `LEGACY_KEYS` публикуется в каталоге
   рядом с `settings_schema` (необязательное поле `legacy_keys`), UI использует его же (§4.6).
2. **D1 и W1.** Модуль `agent/agent/common/intervals.py`: `interval_ms(interval)` (фиксированная
   длительность, `1w` = 7 суток) и `bar_open(ts, interval)` — выравнивание от якоря
   `0` для `s/m/h/d` и `1970-01-05T00:00Z` (понедельник) для `1w`. Потребители:
   - `strategy.py:381` (rescreen): `bar_open(now, tide) + step + buffer`;
   - `strategy.py:417, 553` (cutoff): `bar_open(cutoff + 1, interval) - 1` — `+1` сохраняет
     свечу, закрывающуюся ровно в cutoff;
   - `monitor.py`: только `interval_ms` из общего модуля (вычитание длительностей верно и для
     недели, потому что opens приходят от Binance), своя копия удаляется;
   - `execution/service.py:335` не трогаем: фиксированная минута, не зависит от настроек.
   `1M` (календарный месяц) не поддерживается: `interval_ms("1M")` — `ValueError`.
3. **Правило таймфреймов (D1).** В `coherent()` и в `CONSTRAINTS` правило 16:4:1 заменяется
   на `intervals_ms[tide] > intervals_ms[wave]` и `intervals_ms[wave] > intervals_ms[ripple]`
   (`cmp: gt`, новая грамматика не нужна). Сообщение:
   `"timeframes must satisfy tide > wave > ripple"`.
4. **Семантика cutoff при некратных ТФ.** Код не меняется, семантика фиксируется в
   `STRATEGY_TRIPPLE_SCREEN.md`: прилив и рябь — последний бар, закрытый к
   `trigger.close_time`; **волна — последний бар, закрытый к открытию триггерной ряби**
   (`trigger.open_time`), а не к моменту решения. Пример H12/H6/H4: ripple
   `2026-09-25 04:00–07:59:59.999` берёт wave, закрытую `2026-09-24 23:59:59.999`, хотя к
   решению уже закрылась wave `05:59:59.999`. Это не look-ahead и соответствует спецификации.
   Некратные пары чаще уводят нужный бар за пределы `_merge`-окна → дозагрузка REST в
   `_snapshot`; это покрывается тестом, нагрузка — наблюдением (R-b).
5. **Опубликованные интервалы.** `LOOKUPS["intervals_ms"]` — всё, что агент реально умеет
   (теперь с `1d`, `1w`). Это «множество поддерживаемых» интервалов. Для `quote_asset` множество
   поддерживаемых — `enum` схемы. Далее S(field) — поддерживаемые значения конкретного поля.

### 4.2 Захардкоженные наборы (T5, T6)

- Файл `agent/agent/strategies/tripple_screen/presets.py`: `BUILTIN_PRESETS = {"Default": {...}, "Fast": {...}}`
  в виде явных словарей **со всеми полями схемы** (значения в §5), `const`-поля не входят.
- Тест: множество ключей каждого набора — ровно не-const поля схемы;
  `TripleScreenSettings.model_validate(BUILTIN_PRESETS["Default"]) == TripleScreenSettings()`
  (сравниваются валидированные модели, const в обеих берётся из схемы); каждый набор проходит
  `model_validate` и опубликованные `CONSTRAINTS`.
- Наборы публикуются в каталоге рядом с `settings_schema`: `"presets": [{"name", "params"}]`.
  Поле необязательное, `CATALOG_VERSION` остаётся 1: `CompiledCatalog` сравнивает версию
  на строгое равенство (`strategy_catalog.py:478`), и при версии 2 backend, выкаченный
  раньше агента, отверг бы каталог целиком, то есть и Start.
- Разбор `presets` в backend **изолирован от компиляции каталога**: его ошибки логируются,
  каталог и Start продолжают работать. Итог разбора — одна из форм:
  - `absent` — поля нет (старый агент);
  - `malformed` — поле не список или у каталога нет `published_at`: ничего не принимается;
  - `list` — список записей; каждая запись либо `accepted`, либо `rejected` (с именем, если
    его удалось прочитать), либо нечитаемая (без имени).
  Запись принимается, если после перевода `legacy_keys` её ключи — **ровно** не-const поля
  схемы (лишний ключ, в том числе const, или недостающий → `rejected`) и params проходят
  compiled-модель и `CONSTRAINTS` по тому же конвейеру, что Start (§4.3.5, без шага списков:
  встроенный набор не должен пропадать из-за правки списков, его `valid` считается отдельно).
  Полнота проверяется до синхронизации, поэтому `{}` не заменит полный снимок за счёт
  дефолтов модели.
- Почему в агенте: он единственный владелец параметров (принцип `protocol.py`). Отдельная
  копия в backend-миграции устарела бы при первом же изменении дефолтов.

### 4.3 Backend: БД и API

#### 4.3.1 Таблицы

Модели SQLModel с явным `__tablename__`, миграция Alembic с теми же именами (неявные имена
здесь расходятся: ср. `signalposition`). Все timestamp — `timestamptz`, JSON — `JSONB`.

```
strategy_preset
  id                   uuid pk
  strategy             varchar(64) not null        -- "tripple_screen"
  name                 varchar(64) not null        -- хранится после trim
  params               jsonb not null              -- полный снимок (§4.3.3)
  is_builtin           bool not null default false
  retired_at           timestamptz null            -- builtin, пропавший из каталога
  created_by           uuid null references "user"(id) on delete set null
  created_at, updated_at  timestamptz not null
  unique index ux_strategy_preset_name on (strategy, lower(name))

strategy_builtin_sync                              -- водяной знак синхронизации (§4.3.2)
  strategy      varchar(64) primary key
  published_at  timestamptz not null   -- последняя принятая публикация; начальное '-infinity'
  content_hash  varchar(64) not null   -- sha256 канонического JSON presets; начальное ''
  status        varchar(16) not null   -- never | ok | partial
  errors        jsonb not null default '[]'  -- [{name, type}] для rejected / name_conflict
  synced_at     timestamptz not null

strategy_field_options
  strategy      varchar(64) not null
  field         varchar(64) not null   -- quote_asset / tide_interval / wave_interval / ripple_interval
  options       jsonb not null         -- упорядоченный список строк (коды Binance: "4h", "1d", "1w")
  updated_at    timestamptz not null
  primary key (strategy, field)
```

- Миграция создаёт таблицы и заполняет начальные списки значениями из T2 (коды Binance;
  `W1` = `1w`). Агент и Redis для неё не нужны; upgrade проходит и на пустой, и на
  существующей БД.
- Удаление пользователя не удаляет его наборы (`ON DELETE SET NULL`), изменений в
  `users.py:delete_user` не требуется.

#### 4.3.2 Синхронизация встроенных наборов

- Отдельная функция `sync_builtin_presets(session, strategy, parsed, published_at, content_hash)`,
  не часть компиляции и не часть кеша каталога. Вызывается из `GET presets/`. Свежесть
  определяет **водяной знак** в `strategy_builtin_sync`, общий для всех воркеров; хеш
  содержимого (`presets` без `published_at`) — только признак «то же содержимое».
- Форма разбора `absent` → синхронизация не выполняется, ничего не меняется (в том числе
  водяной знак). `malformed` → то же плюс ошибка в лог.
- Для `list` — **одна транзакция**:
  1. `INSERT INTO strategy_builtin_sync … ON CONFLICT DO NOTHING` (начальная строка
     `published_at = '-infinity'`, `status = never`), затем `SELECT … FOR UPDATE` — воркеры
     синхронизируются по этой строке;
  2. `incoming < published_at` → `stale`: ничего не меняется, rollback;
     `incoming = published_at` и хеш совпадает → `noop` (уже применил другой воркер);
     `incoming = published_at` и хеш другой → ошибка в лог, ничего не меняется;
  3. иначе для каждой `accepted` записи: `INSERT … ON CONFLICT (strategy, lower(name)) DO UPDATE
     SET params, retired_at = NULL, updated_at = now() WHERE strategy_preset.is_builtin AND
     (strategy_preset.params IS DISTINCT FROM excluded.params OR strategy_preset.retired_at IS NOT NULL)
     RETURNING id`. Пустой `RETURNING` неоднозначен (no-op или чужая строка), поэтому
     существующие строки с этими именами читаются в той же транзакции до upsert. Если строка
     пользовательская (`is_builtin = false`), она не трогается, в `errors` пишется
     `{name, type: "name_conflict"}`;
  4. retirement — **только если список авторитетный** (нет `rejected` и нечитаемых записей):
     `UPDATE … SET retired_at = now(), updated_at = now() WHERE strategy = :s AND is_builtin
     AND retired_at IS NULL AND lower(name) NOT IN (:accepted_names)`. Явный `[]` —
     авторитетный список: все встроенные уходят в `retired_at`. При неавторитетном списке
     строка отклонённой записи не меняется (не обновляется и не скрывается);
  5. водяной знак := `incoming`, хеш, `status = ok`, если нет `rejected`/`name_conflict`,
     иначе `partial` с `errors`; commit.
  Итог: id стабилен; no-op не трогает `updated_at` строк наборов, но **продвигает водяной
  знак**; запоздавший писатель (`B@20` после `A@30`) отвергается целиком — и upsert, и
  retirement. `NULL` в свежести не бывает: поле `not null`, начальное `-infinity`.
- Кеш в процессе: пара `(published_at, content_hash)` запоминается только после commit или
  исхода `stale`/`noop`, поэтому ошибка БД повторяется на следующем запросе, в том числе при
  cache hit каталога. Воркер со старым кешем каталога получает `stale` и ничего не пишет.
- `GET presets/` возвращает состояние синхронизации (§4.3.4); UI при `partial` показывает
  предупреждение со списком `errors`.
- Наборы с `retired_at` в `GET presets/` не возвращаются; при возврате набора `retired_at`
  снимается, id прежний.
- Ошибка синхронизации **не блокирует Start**: логируется, Start проверяется как обычно.
- UI не требует наличия `Default` в БД: если встроенных наборов нет (старый агент), селектор
  показывает только пользовательские и `— текущие параметры запуска —`.
- Списки (`strategy_field_options`) не кешируются: читаются из БД в каждом запросе, так что
  правка сразу действует во всех воркерах.

#### 4.3.3 Набор — полный снимок

- `POST`/`PUT` материализуют набор: backend валидирует params (§4.3.5), подставляет дефолты
  схемы для отсутствующих не-const полей и сохраняет **все** не-const поля. Сохранённый набор
  не зависит от последующей смены дефолтов агента.
- Дрейф схемы при чтении (`GET presets/`, пересчёт `valid/errors`). Сначала ключи
  переводятся по `legacy_keys` текущего каталога (общий helper backend `apply_legacy_keys`,
  то же правило коллизий, что в агенте §4.1.1: оба имени с разными значениями → ошибка
  `legacy_conflict`), затем множество ключей сравнивается с **не-const** полями схемы:
  - нет не-const поля (новое поле) → `valid=false`, `missing_in_preset` на поле. UI
    подставляет дефолт, если он есть в схеме, и показывает `(изменён)`; поле без дефолта
    остаётся пустым и невалидным, ничего не выдумывается;
  - есть ключ, которого нет среди не-const полей (поле удалено, стало const или ключ
    неизвестен) → `valid=false`, `unknown_param`;
  - изменение дефолта в агенте на сохранённый набор не влияет.
  GET только читает: строка в БД остаётся со старыми ключами до следующего `PUT`, который
  сохранит уже новые имена. `POST`/`PUT` со старым ключом отклоняются так же, как Start
  (`422`, UI старые ключи не отправляет).

#### 4.3.4 API и матрица ответов

Префикс `/trading/strategies/{strategy}/`. **Общие правила** (применяются по порядку ко всем
новым endpoint, исключения — в таблице):
1. не superuser → `403`;
2. «каталог недоступен» — это и отсутствие/непригодность каталога, и ошибка Redis: у них один
   исход;
3. strategy известна, если она есть в каталоге; при недоступном каталоге — если для неё есть
   строки в `strategy_field_options` (миграция засевает `tripple_screen`). Иначе → `404`
   (Start сохраняет свой нынешний `422` для неизвестной стратегии, его контракт не меняется);
4. ошибка БД → `503`;
5. `IntegrityError` → `409` **только** при нарушении `ux_strategy_preset_name` (проверяется имя
   constraint), с rollback сессии; любой другой `IntegrityError` — ошибка сервера (`500`, лог).

Имя набора: trim, 1–64 символа; `Default`/`Fast` зарезервированы без учёта регистра и
пробелов вокруг — при POST и при переименовании через PUT, даже если синхронизации ещё не было.
Id ищется вместе со strategy; `field` — только из четырёх полей со списками.

| Endpoint | Успех | Ошибки / без каталога |
|---|---|---|
| `GET presets/` | `200 {items: [{id, name, is_builtin, params, valid, errors}], builtin_sync: {status, published_at, errors}}` | без каталога → `200`, `valid=null`, `errors=[]`, синхронизация не выполняется |
| `POST presets/` | `201` | невалидные params → `422`; имя занято/зарезервировано → `409`; без каталога → `503` |
| `PUT presets/{id}` | `200` | id не найден в этой strategy → `404`; builtin → `409`; остальное как POST |
| `DELETE presets/{id}` | `204` | не найден → `404`; builtin → `409`; без каталога работает |
| `GET options/` | `200 {field: {options, unsupported}}` | без каталога → `unsupported=null` (неизвестно, не `[]`) |
| `PUT options/{field}` | `200 {options, unsupported}` | пустой список, пустая строка, дубликат после нормализации → `422`; неизвестный field → `404`; без каталога (в том числе при ошибке Redis) сохраняется (D3), `unsupported=null` |

`unsupported = options − S(field)`. Формат ошибок — `422 {detail: [{loc, msg, type}]}`, единый
для Start и новых API: поле → `loc = ["body", "params", <field>, …]`, межполевое правило и
неизвестный ключ → `["body", "params"]`, имя → `["body", "name"]`. Сейчас ошибки поля у Start
имеют `loc = [<field>]` без префикса (`strategy_catalog.py:423–432`, `loc` модели), правило —
`["body", "params"]`; общая функция §4.3.5 добавляет префикс, и это меняет формат Start. UI
`loc` ответа Start не разбирает (ошибки показываются по `msg`), тест backend фиксирует новый
формат.

#### 4.3.5 Проверка на Start и при сохранении

`_enforce_strategy_params` (общий для обоих Start-маршрутов), сохранение набора и приём
встроенных наборов (§4.2, без шага 5) используют одну функцию-конвейер. Шаг с ошибками
останавливает конвейер, кроме шагов 4 и 5 — их ошибки собираются вместе:
1. **Поля** — compiled-модель. Типы строгие: целое поле принимает только JSON integer (не
   `bool`, не строку, не float), decimal — строку или JSON number, но не `bool`/`null`.
   Сейчас модель lax (`true` проходит как `1`); строгость задаётся при компиляции схемы.
2. **Канонические значения** = выход модели (с дефолтами схемы), а не сырой `params`. Дальше
   всё считается по ним, поэтому проверенное и вычисляемое представления совпадают.
3. **Поддерживаемость:** для полей со списком значение ∈ `S(field)`, иначе ошибка поля
   `unsupported_value` (`422`). Идёт до `CONSTRAINTS`, поэтому `ripple_interval="1M"` не
   доходит до отсутствующего лукапа (сейчас это `CatalogError` → `503`).
4. **`CONSTRAINTS`** по каноническим значениям. `CatalogError` здесь теперь означает только
   дефект каталога → `503`.
5. **Списки:** значение ∈ `options(field)`. Если строки списка для поля нет в БД → проверки
   нет (остаётся S из шага 3). Ошибка чтения БД → `503`, не fallback.
   Так `{}` при списке quote asset `["USDC"]` отклоняется из-за эффективного `USDT`.
6. При отказе нет enqueue и нет записи в `desired`.
В Redis уходит исходный payload (как сейчас), канонические значения нужны только для проверки.

Для сохранения набора шаг 3 — да (T1: сохранить можно только годный к запуску набор).
D3 при этом не нарушается: неподдерживаемые значения можно сохранить **в список**, но не в набор.

### 4.4 Отображение интервалов и редактор списков

В БД и API хранятся коды Binance (`1w`, `1d`, `12h`, …, `1m`). UI показывает их как
`W1, D1, H12, …, M1`. Нормализация ввода в редакторе списков (`normalizeInterval` в
`strategySchema.ts`), по порядку:
1. trim; пустая строка — ошибка;
2. точное совпадение с кодом Binance из S (регистр важен: `1m` — минута, `1M` — месяц);
3. метка строго вида `^[MHDW][0-9]+$` (верхний регистр) → код (`H1 → 1h`, `M1 → 1m`, `W1 → 1w`);
4. всё остальное сохраняется **как есть** и помечается unsupported (D3): `custom`, `1M`, `m1`.
Дубликаты проверяются после нормализации (`H1` и `1h` — дубликат). Для `quote_asset` —
только trim. Порядок опций задаётся списком из БД (от старшего ТФ к младшему, как в T2).

### 4.5 Frontend

1. **Выбор набора (T3)** — `Select` над полями: встроенные наборы идут первыми и помечены
   `built-in`. При выборе базовые параметры **заменяются** params набора (после перевода
   `legacy_keys`), ничего из прежнего `desired` не подмешивается. Если после этого поле
   изменить, в селекторе показывается `<имя> (изменён)`; сравнение — по не-const полям
   после нормализации. Кнопки: **Save as…** (диалог с именем), **Update** (только для своих),
   **Delete** (с подтверждением, только для своих). Невалидный набор можно выбрать, его
   ошибки сразу видны у полей. Начальное состояние: если параметры из `status.desired`
   совпадают с каким-то набором, выбран он; иначе `— текущие параметры запуска —`. Если
   снапшота нет — `Default`, если он есть, иначе значения по схеме.
2. **Поля со списком (T2)** — настоящий `Select` вместо `Input + datalist`. Опции берутся
   из списка БД. Опция вне S видна, но неактивна (disabled) с подсказкой «агент не
   поддерживает». Значение, которого нет в списке (например, из старого набора), показывается
   с ошибкой поля.
3. **Валидация (T1).** `validateSettings` получает дополнительно `options` и `supported` и
   проверяет принадлежность спискам сам, не полагаясь на `Select`. Результат хранит
   состояние `pending | unavailable | valid | invalid` и ключ контекста
   (`draft`, версия схемы, версия списков). Проверка запускается:
   - на каждое изменение поля (дебаунс ~200 мс) — для показа ошибок;
   - **синхронно перед каждой отправкой** — Start, подтверждение live-Start, Save as, Update —
     по точному итоговому payload; подтверждение live-Start перепроверяет payload и
     отменяется, если контекст (схема, списки) изменился;
   - при загрузке `desired`, выборе набора, обновлении каталога и списков (даже если форма
     не редактировалась).
   Каталог или списки не загрузились → `unavailable`, Start и Save недоступны. Backend
   проверяет повторно и остаётся последним рубежом (другой администратор мог поменять списки).
4. **Payload.** `validateSettings` возвращает только поля схемы (`parsed` + const), без
   `savedParams`: неизвестные ключи из `desired` в Start не попадают (backend всё равно
   отвергает extras). Тест `trading-contract.spec.ts:295–299` (`future_param`) переписывается
   на обратное: неизвестный ключ не отправляется.
5. **Числа.** Разбор без `Number()` для проверки формата: целые — `^[+-]?\d+$` и
   `Number.isSafeInteger`; decimal — `^[+-]?(\d+(\.\d*)?|\.\d+)([eE][+-]?\d+)?$`, отправляются
   строкой, границы `gt/ge/lt/le` сравниваются точным десятичным сравнением строк (маленький
   helper, без float). Правило: UI может быть строже backend (например, целое > 2^53−1), но
   никогда не мягче (`0x10`, `Infinity`, пробелы внутри — ошибка).
   **Точны и `CONSTRAINTS`:** evaluator (`strategySchema.ts:318–369`) переводится с `Number` на
   точный decimal (мантисса `BigInt` + масштаб). Грамматика сейчас — `const`, `field`,
   `lookup` и операторы `add/sub/mul/max` (`schema.py:70–135`): все точны без округления.
   Неизвестный оператор или нечисловое значение → `unavailable` (fail closed), как и сейчас
   `undefined`. Сравнение для `(изменён)` — по тем же точным значениям (`"1.0"` равно `"1"`).
6. **EMA tide periods** — три числовых поля a / b / c вместо текста через запятую.
   Правило a < b < c уже опубликовано (`CONSTRAINTS`), новое только в отображении.
7. **Блок «Списки выбора» (T2)** — отдельная карточка на той же странице, свёрнута по
   умолчанию. Для каждого из четырёх полей: чипы значений, поле «добавить», удаление и
   перестановка, кнопка Save. Нормализация по §4.4; значения вне S сохраняются с
   предупреждением (D3). Удаление значения, которое используется в сохранённом наборе,
   разрешено, но набор после этого становится `valid=false`, и UI об этом предупреждает.
   Сохранение списка не блокируется валидацией формы наборов.

### 4.6 Миграция старых имён и порядок выкладки

- **UI:** `seedFormValues` и загрузка набора переводят ключи по `legacy_keys` из каталога
  (`swing_low_h1_n=7` → `swing_low_wave_n=7`), старые ключи в payload не попадают (§4.5.4).
  Если каталог обновился при dirty-форме, черновик не выбрасывается и не пропускается: его
  ключи переводятся по новым `legacy_keys`, неизвестные удаляются, результат
  перепроверяется, над формой — баннер «схема агента изменилась».
- **Агент:** §4.1.1 — старые ключи в `desired`, в очереди команд и в снапшоте восстановления.
- **Backend:** имён полей не хардкодит, но переносит `legacy_keys` без знания их содержимого:
  `CompiledStrategy.legacy_keys` (изолированный разбор, неверная форма → `{}` и лог) →
  `StrategyDescription.legacy_keys` в `GET /trading/strategies/` → `_catalog_response` →
  сгенерированный клиент. Он же переводит ключи сохранённых наборов при чтении (§4.3.3) и
  встроенных при приёме (§4.2).
- **Модель выкладки.** Стек деплоится целиком из одной ревизии (`scripts/deploy.sh`,
  `docs/DEPLOY.md` §2), так что разные версии backend и агента встречаются только
  (а) если master выкачен между задачами серии, (б) в открытых до деплоя вкладках со старым
  JS, (в) при откате. Поэтому «порядок не важен» не обещается, вместо этого — правила:
  - **G1. Каждая задача оставляет master деплоебельным.** Отсюда PRESET-01 — не только
    агент: в той же задаче backend пробрасывает `legacy_keys`, UI переводит ключи при seed и
    не подмешивает `savedParams`. Задачи, которые без этого ломали бы Start, в одиночку не
    выкатываются.
  - **G2. Старая вкладка — окно с блокировкой, без вреда.** Старый JS отправляет старые
    ключи из `savedParams` вместе с новыми (`strategySchema.ts:464`), refetch каталога
    его не исправляет. Backend отвечает `422` без enqueue; если лишний ключ есть в
    `legacy_keys`, `msg` говорит: `"parameter 'swing_low_h1_n' was renamed to 'swing_low_wave_n';
    reload the page"`. Несохранённый черновик такой вкладки теряется при перезагрузке —
    известное ограничение, пишется в release notes.
  - **G3. Откат за PRESET-01 или PRESET-05a — только по runbook** (ниже).
- **Runbook отката** (PRESET-09, в `docs/DEPLOY.md` §6). Откат, выполненный после автоматического
  resume, запаздывает: старый агент при boot сам восстанавливает running `desired`
  (`commands.py:549–572`) — новые имена молча превратятся в дефолты `2/2`, `Fast` и
  `1d/1w` будут отвергнуты. Поэтому **до** отката:
  1. Stop через UI/API; дождаться `status.state = idle` и `running = false` в runtime-снапшоте
     (`engine.py:54`): тогда агент после boot остаётся idle (`engine.py:8`). На время отката
     Start не нажимается (один оператор);
  2. записать текущие параметры из `desired` (для справки и возврата вперёд);
  3. если откат пересекает PRESET-05a: снять дамп и выполнить `alembic downgrade` до ревизии
     цели **новым** кодом — иначе старый backend при `prestart` не найдёт head-ревизию и не
     поднимется; наборы и списки при этом удаляются (они в дампе);
  4. `git checkout <ревизия> && ./scripts/deploy.sh`;
  5. Start с конфигурацией старой версии (старые имена, 16:4:1, без `1d/1w`). Её проверяет
     уже старый каталог, опубликованный старым агентом, так что несовместимый Start не
     пройдёт.

**Общая фикстура граничных случаев** — `tests/fixtures/validation-edge-cases.json`, массив
кейсов. У одного и того же литерала разные представления дают разные тесты, поэтому кейс
описывает вход на каждом уровне отдельно:

```json
{
  "id": "decimal-precision-string",
  "note": "Decimal строкой сохраняет точность: ge 0, lt 100 — допустимо; тот же литерал числом — отдельный кейс (float → 100.0 → bound)",
  "ui_draft": {"stop_buffer_pct": "99.999999999999999999"},
  "wire": "{\"stop_buffer_pct\": \"99.999999999999999999\"}",
  "expected_sent": {"stop_buffer_pct": "99.999999999999999999"},
  "expected_normalized": {"stop_buffer_pct": "99.999999999999999999"},
  "outcomes": {
    "ui": {"result": "ok"},
    "backend_start": {"result": "ok"},
    "backend_preset": {"result": "ok"},
    "agent_model_validate": {"result": "ok"},
    "agent_command": {"result": "ok"},
    "agent_resume": {"result": "ok"}
  },
  "intentional_difference": null
}
```

- `ui_draft` — строки, как их ввёл пользователь (`null`, если кейс UI не касается); `wire` —
  **точный текст JSON** (не объект), чтобы различать `"0x10"` строкой, unquoted число,
  unsafe integer (браузер округляет уже в `JSON.parse`) и невалидный JSON;
  `expected_sent` — payload UI; `expected_normalized` — канонические значения (§4.3.5 шаг 2)
  или `null` при ошибке.
- `category`: `type | bound | constraint | unsupported | option | unknown_param |

## 8. Риски и открытые вопросы

- **R-a. Длина истории (D4).** Screening и snapshot требуют ровно `kline_window` закрытых
  непрерывных баров каждого ТФ (`strategy.py:260–274, 549–599`), это не только разогрев
  индикаторов. При 1000: W1 ≈ 19,2 года (на Binance Spot практически недостижимо), D1 ≈ 2,7 года.
  Символы с короткой историей не получают **новых входов**; открытые позиции и их мониторинг
  не затрагиваются. Предложение: под полями ТФ всегда показывать требуемую историю
  (`kline_window × интервал` для tide/wave/ripple) и минимально допустимый `kline_window`
  по `CONSTRAINTS`; жёлтое предупреждение (без блокировки и без автоизменения окна), если
  история tide больше **1 года** (D4). Реализация — PRESET-07.
- **R-b. Некратные таймфреймы (D1).** Разрешены пары вроде H6/H4 и H12/H6/H4. Корректность
  выбора баров покрывается тестами (PRESET-03), смысл сигнала на таких парах на истории не
  проверялся; дозагрузка REST на некратных парах чаще — наблюдать по логам
  `history not ready` и REST-метрикам.
- **R-c. Дрейф схемы.** Набор — полный снимок (§4.3.3); новое/удалённое поле делает его
  `valid=false`, изменение дефолта на него не влияет. Молча ничего не заполняется.
- **R-d. Свободные списки (D3).** В список можно внести значение, которое агент не
  поддерживает. Защита — предупреждение при сохранении, disabled-опция и `422` на Start.
- **R-e. Окно выкладки и откат** — §4.6: правила G1–G3, runbook отката (PRESET-09). Откат
  без предварительного Stop возобновит стратегию с дефолтами вместо переименованных полей.
- **Не цели v1:** наборы для execution-настроек; имя набора в Start-снапшоте и Status;
  история изменений наборов; права доступа к наборам по пользователям (все superuser видят
  все наборы).
