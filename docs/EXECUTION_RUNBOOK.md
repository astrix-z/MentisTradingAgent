# Runbook исполнения ордеров

Действия оператора при сбоях реального исполнения (план `docs/ORDER_EXECUTION_PLAN.md`
§9.7). Файл пополняется до live-пилота. Остальные разделы из §9.7 пока не написаны:
недоступны БД/Redis/биржа, HALT/delisting символа с позицией, 429/418, рассинхрон
часов, ручная сверка с историей ордеров.

## 1. Вход завис в UNKNOWN после ручной покупки того же символа

### Симптом

- В heartbeat висит алерт `unknown`:
  `order mta-<…>-e<n> (<SYMBOL>) outcome unknown for <N>s; not retried`.
  Он появляется через `unknown_escalate_s` (по умолчанию 120 с) после попытки.
- Intent входа в состоянии `unknown`. Резерв USDT, слот и символ заняты.
- Есть незавершённая работа, поэтому Start на другой сети или аккаунте отклоняется.
- Обычно рядом висят `foreign_trades:<SYMBOL>` (сделка чужого ордера) и
  divergence по балансу: купленный актив не объясняет ни одна позиция. Пока висит
  divergence, admission закрыт.

### Почему так

Если исход BUY агента неизвестен (например, timeout), агент проверяет ордер по
client id. Отсутствие ордера считается доказанным, только если выполнены три
условия: ордер не найден минимум дважды; с момента попытки прошло больше
`recvWindow` + 60 с; с момента попытки (с запасом 5 с) по символу не исполнилась
BUY-сделка ордера, который агент не может назвать. Последнее условие нужно потому,
что принятый биржей ордер какое-то время может не находиться запросом.

Ручная покупка того же символа (в приложении Binance, другим ботом или по API)
выглядит для агента как такая сделка. Отличить её от своего невидимого ордера агент
не может, поэтому вход остаётся UNKNOWN и повторно не отправляется. Это осознанный
консервативный выбор. Ошибочное освобождение стоило бы позиции на бирже без учёта и
без OCO, а удержание стоит только занятого резерва.

Само это состояние не пройдёт: ручная сделка остаётся в недавней истории символа,
которую читает агент.

### Профилактика

Аккаунт выделен под агента (§9.6): вручную на нём не торгуют. Особенно нельзя
покупать символ, по которому у агента есть вход в `unknown` или `submitted`.

### Действия

1. Ничего не покупать и не продавать по символу. Вход вручную не повторять.
2. Взять client id из алерта и найти его в истории ордеров Binance:
   Orders → Order History, либо `GET /api/v3/order?symbol=<SYMBOL>&origClientOrderId=<id>`.
3. **Ордер найден** — это вход агента. Ничего не трогать: как только биржа отдаст
   ордер по запросу, агент сам проведёт его (позиция, OCO либо освобождение при
   `EXPIRED`). Агент спрашивает биржу каждый раунд исполнения. Если ордер виден на
   бирже, а алерт держится несколько минут, передать разработчику client id и вывод
   запроса.
4. **Ордера нет**, а BUY-сделка из `foreign_trades` принадлежит ордеру без префикса
   `mta-`, значит вход не размещался и сделка ручная.
   - Ручную покупку убрать, как решит владелец: продать или вывести. Divergence по
     балансу снимется, когда следующая проверка его не найдёт.
   - Сам UNKNOWN-вход агент не освободит. Освободить его можно командой
     `release_entry`. В UI: страница Strategy → карточка «Unresolved entry» (она
     видна, пока висит алерт `unknown`; client id подставлен из алерта) → «Release
     entry» → подтвердить. Через API: `POST /api/v1/trading/commands/` с телом
     `{"type": "release_entry", "payload": {"client_order_id": "<id из алерта>"}}`.
     Агент сам проверяет, что ордера нет: запрос старше `recvWindow` + 60 с,
     биржа не знает client id, у каждой непонятной BUY-сделки после попытки ордер
     с чужим client id (не `mta-`) — история читается вся, от времени попытки,
     постранично, — и баланс базового актива сверх открытых позиций и этих чужих
     сделок меньше количества входа (сделка, которую биржа ещё не показывает,
     видна в балансе). Только тогда intent освобождается с причиной
     `released_by_operator`, а алерт `unknown` снимается. Любое сомнение даёт отказ
     `not released: <причина>`, и ничего не меняется. Отказ «too recent» значит
     повторить позже. «is on the exchange» — вернуться к шагу 3. «cannot identify
     order» или «may be ours» — ордер может быть нашим: передать разработчику
     client id и текст отказа. «may have filled» — на балансе есть столько актива,
     сколько купил бы вход, и чужие сделки этого не объясняют: либо вход исполнен,
     а биржа ещё не показывает его сделку, либо актив пришёл не сделкой (перевод).
     Повторить позже; если держится — передать разработчику.

## 2. Откат на ревизию без исполнителя (T0 и всё до `e133313`)

### Симптом

- Нужно откатить сервер на ревизию, в которой нет исполнения ордеров, например на T0
  `567f4f8` (`docs/DEPLOY.md` §6).
- `deploy.sh --revision <цель>` падает на шаге `(2a) барьер исполнения` с
  `откат на <цель> запрещён`, а в логе выкладки есть строки
  `barrier: unfinished execution <account>/<network>: positions=… intents=… attempts=…`.

### Почему так

Stop закрывает только admission: остановленный движок продолжает вести реальные
позиции (OCO, trailing, выход по времени, guard) и разрешать UNKNOWN-входы. Признаки
барьера доставки (`succeeded`, `lag = 0`, `pending = 0`, `idle`) выполняются и при
открытой позиции. В ревизии без исполнителя этого делать некому: OCO на бирже может
остаться, но позицию никто не сопровождает. БД агента при откате не меняется, поэтому
записи сохраняются, но работа по ним останавливается.

Незавершённая работа — то же, что считает `ExecutionRuntime.unfinished`, во всех
контекстах (аккаунт и сеть): позиция не в `closed`, intent в `reserved`, `submitted`
или `unknown`, попытка ордера в `prepared`, `sent` или `unknown`.

### Что делать

1. Не откатывать. Прежний агент уже поднят снова, флаг `trading:start_fence` стоит.
2. Проверить самому: `$COMPOSE exec -T agent python -m agent.execution.barrier`.
   Код 0 значит, что работы нет. Код 1 выводит список. Код 2 значит, что БД агента
   не прочитана: это не доказательство, откат запрещён.
   Если работает уже агент цели (прежний откат упал после `up`), модуля барьера в
   нём нет — тогда ответ даёт повторный `deploy.sh`: на шаге (2a) он спрашивает образ
   `releases/current`, у которого исполнитель есть.
3. Довести работу до конца текущей ревизией:
   - позиции закроются сами по OCO, trailing или выходу по времени (до 8 ч); раньше
     их можно закрыть из UI (`close_position`);
   - UNKNOWN-вход разрешится сам, когда биржа ответит; ручной случай описан в §1;
   - если `intents` или `attempts` держатся без алерта `unknown`, передать разработчику
     вывод барьера: откат до их разрешения запрещён.
4. Когда барьер даёт код 0, повторить откат по `docs/DEPLOY.md` §6 с шага 1. После
   Stop новой работы не появляется, поэтому код 0 окончателен.

## 3. Включить или выключить реальные сделки

Реальные сделки включаются отдельным переключателем владельца. Выбор сети и Start
их не включают и не выключают (ClickUp 869fgqxah, план §4.3).

### Где

UI: страница Strategy, карточка «Real trading». API: `POST /api/v1/trading/execution/`
с телом `{"settings": {"enabled": true, ...лимиты}}`. Текущее желаемое состояние —
`GET /api/v1/trading/execution/`, фактический режим агента — `actual.execution.mode`
в `GET /api/v1/trading/status/` (`off`, `enabled`, `paused(<причина>)`).

### Включить

1. Проверить, на какой сети работает стратегия: в диалоге включения она названа
   (на LIVE — «with real money»).
2. Проверить лимиты в блоке «Limits»: `max_symbols`, `slot_quote`, `position_share`,
   `daily_losing_trades_limit`, `max_slippage_pct` и остальные.
3. Включить и подтвердить. Watchdog агента (раз в 5 с) берёт lock и начинает
   сверку с биржей. Сверка проверяет каждый актив на счёте и может занять минуты:
   на testnet с ~490 тестовыми активами — около 150 с (ClickUp 869fgqu5u). Пока
   она идёт, режим — `paused(no_execution_lock)`, входы закрыты, а Start ждёт её
   окончания.
4. Включение при работающей стратегии не на USDT backend отклоняет сразу (422),
   и оно не сохраняется. Start не на USDT при включённых сделках тоже получает 422. Если агент всё же откажет (например, БД агента не мигрирована),
   причина видна в результате команды на карточке, а агент остаётся в режиме
   `off`. В сохранённых настройках при этом стоит ON, и при рестарте агент
   попробует применить их снова. Чтобы этого не было, выключите переключатель.
   Если при boot сохранённое ON несовместимо со стратегией, которую агент
   поднимает (не USDT), стратегия поднимается, сделки остаются выключены, а в
   heartbeat появляется алерт `settings`.

### Выключить

Выключение подтверждения не требует. Команда выключения встаёт в очередь за
Start/Stop и может ждать текущий Start. Чтобы немедленно остановить новые входы,
сначала нажмите «Pause entries»: эта команда выполняется вне очереди.
После выключения новые входы прекращаются сразу. Открытые
позиции, их защита и выходы продолжают сопровождаться. Lock агент отпускает,
только когда незавершённой работы не осталось.

Пауза («Pause entries») только приостанавливает новые входы до «Resume entries» и
не переживает рестарт агента. Переключатель рестарт переживает: он хранится в
`agent:execution`.

## 4. Права ключа и торговые группы Binance

### Как Binance описывает права

- **Права аккаунта** — поле `permissions` в `GET /api/v3/account`. Обычный
  spot-аккаунт получает `SPOT`. Аккаунт в торговой группе Binance получает
  вместо `SPOT` только имя группы, например `TRD_GRP_072`. Это нормально, а не
  отказ прав. Группа может смениться без нашего участия.
- **Права символа** — поле `permissionSets` в `GET /api/v3/exchangeInfo`. Это
  список наборов. Аккаунт может торговать символом, если у него есть хотя бы
  одно право **из каждого** набора (И по наборам, ИЛИ внутри набора). Старое
  поле `permissions` у символа Binance больше не заполняет; агент читает его,
  только если `permissionSets` нет.
- Подробности: [Spot API CHANGELOG](https://developers.binance.com/docs/binance-spot-api-docs/CHANGELOG)
  и [Spot testnet CHANGELOG](https://developers.binance.com/docs/binance-spot-api-docs/testnet/CHANGELOG).

Пример: `permissionSets=[["SPOT","TRD_GRP_072","TRD_GRP_073"]]` разрешает
аккаунту с `permissions=["TRD_GRP_072"]` торговать символом. Набор без 072 его
запрещает.

На 2026-10-16 live-аккаунт имеет `permissions=["TRD_GRP_072"]`, `canTrade=true`.
Группа 072 разрешена на 510 из 511 USDT-пар. Не разрешена RWUSDUSDT.

### Что проверяет агент

1. **Ключ** — при старте runtime и раз в 5 минут (`ACCOUNT_CHECK_EVERY`):
   `canTrade=true` и непустые `permissions`. `SPOT` не требуется. Если
   проверка не прошла, в heartbeat появляется алерт `key`:
   `API key cannot trade spot (canTrade=…, permissions=[…])`. Пока он висит,
   новые входы закрыты (fail-closed). Выходы и защита открытых позиций
   продолжают работать.
2. **Символ** — на каждом входе (`check_symbol` в `agent/agent/execution/sizing.py`):
   права аккаунта сверяются с `permissionSets` символа. Если символ не
   разрешён, вход отклоняется без ордера. В `execution_intent` он получает
   `state=REJECTED` и `reason=symbol_not_permitted`, а в деталях — права
   аккаунта и символ.

Список символов стратегии права не фильтруют: скрининг идёт по всем символам, а
отказ происходит только при попытке входа.

### Как проверить вручную

Права аккаунта (подписанный запрос, ключи из окружения агента; на сервере —
из каталога `releases/current`):

```bash
docker compose exec agent python -c "
import asyncio
from agent.exchange.rest import ExchangeRest
a = asyncio.run(ExchangeRest.connect('live').account())
print('canTrade', a.can_trade, 'permissions', a.permissions)"
```

Наборы прав символа (без ключа):

```bash
curl -s 'https://api.binance.com/api/v3/exchangeInfo?symbol=BTCUSDT' \
  | jq -c '.symbols[0].permissionSets'
```

Какие торгуемые USDT-пары закрыты для группы (подставьте свою; та же логика,
что в агенте: право из каждого набора):

```bash
curl -s 'https://api.binance.com/api/v3/exchangeInfo' | jq -r --arg g TRD_GRP_072 '
  .symbols[] | select(.quoteAsset=="USDT" and .status=="TRADING")
  | select(any(.permissionSets[]; index($g) == null)) | .symbol'
```

### Действия

- **Алерт `key` с `canTrade=false` или пустыми `permissions`.** Ключ или аккаунт
  ограничены на стороне Binance. Проверьте ключ в кабинете Binance: должна быть
  включена Spot Trading, IP сервера должен быть в whitelist. Без этого не
  включайте реальные сделки. Алерт снимается сам при следующей проверке (до
  5 минут) или при рестарте агента.
- **Много `symbol_not_permitted`.** Скорее всего, Binance перевела аккаунт в
  другую группу. Сравните `permissions` аккаунта с `permissionSets` отклонённых
  символов. Код менять не нужно: агент сверяет права на каждом входе.
- **Единичный `symbol_not_permitted`.** Символ закрыт для группы аккаунта (как
  RWUSDUSDT). Действий не нужно; при желании уберите символ из списка
  стратегии.
