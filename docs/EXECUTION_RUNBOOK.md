# Runbook исполнения ордеров

Действия оператора при сбоях реального исполнения (план `docs/ORDER_EXECUTION_PLAN.md`
§9.7). Разделы §5–§9 описывают поведение кода на `development` от 2026-10-17;
при изменении кода исполнения их нужно сверять заново.

## 0. Где смотреть состояние исполнения

Команды ниже выполняются на сервере из `~/apps/mentis-trading-agent`.
`COMPOSE` — `docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml`
(как в `docs/DEPLOY.md` §6).

- **UI**, страница Strategy: строка «Real trading» показывает режим агента
  (`off`, `on — placing orders`, `on, entries held: <причина>`), блок сообщения
  агента — алерты. Сообщение агента показывает алерты исполнения, только если
  у движка стратегии нет своего сообщения, поэтому полный список берите из
  heartbeat.
- **Heartbeat** (обновляется каждые 5 с, backend считает его устаревшим через 10 с):

  ```bash
  docker exec mentis-redis-1 redis-cli get trading:heartbeat | jq '.execution | {mode, leader, open_positions, alerts}'
  ```

  `mode` — `off`, `enabled` или `paused(<причина>)`; причина — первое, что
  держит входы закрытыми (`ExecutionRuntime.admission_block`). Алерты `schema`,
  `database`, `key`, `clock`, `account`, `lock`, `divergence:*`, `quarantine:*`
  и бан IP (`ip_banned`) закрывают новые входы. Остальные (`bnb`, `feed:*`,
  `guard:*`, `clock_warning`, `foreign_trades:*`, `halted:*` и
  `status_unknown:*` (§6),
  `testnet_balances`, `reconcile`, `context`, `restore`) информируют, но на открытые позиции и их защиту закрытые входы
  не влияют.
  Сверка балансов: актив стоимостью от 5 USDT, который не объясняют открытые
  позиции, на live — `divergence:balance:<SYMBOL>` (входы закрыты), на testnet
  — один алерт `testnet_balances` с числом таких активов (testnet раздаёт
  сотни тестовых активов; входы не закрывает).
- **Лог агента**: `$COMPOSE logs --since 30m agent`.
- **БД агента**: `docker exec -it mentis-db-1 psql -U postgres -d agent`.

Новые входы закрыты — значит, агент не покупает. Защита, trailing, выход по
времени и guard открытых позиций продолжают работать, пока у процесса есть lock
исполнения и связь с БД и биржей.

## 1. Вход завис в UNKNOWN после ручной покупки того же символа

### Симптом

- В heartbeat висит алерт `unknown`:
  `order mta-<…>-e<n> (<SYMBOL>) outcome unknown for <N>s; not retried`.
  Он появляется через `unknown_escalate_s` (по умолчанию 120 с) после попытки.
- Intent входа в состоянии `unknown`. Резерв USDT, слот и символ заняты.
- Есть незавершённая работа, поэтому Start на другой сети или аккаунте отклоняется.
- Обычно рядом висят `foreign_trades:<SYMBOL>` (сделка чужого ордера) и
  divergence по балансу: купленный актив не объясняет ни одна позиция. Пока висит
  divergence, admission закрыт.

### Почему так

Если исход BUY агента неизвестен (например, timeout), агент проверяет ордер по
client id. Отсутствие ордера считается доказанным, только если выполнены три
условия: ордер не найден минимум дважды; с момента попытки прошло больше
`recvWindow` + 60 с; с момента попытки (с запасом 5 с) по символу не исполнилась
BUY-сделка ордера, который агент не может назвать. Последнее условие нужно потому,
что принятый биржей ордер какое-то время может не находиться запросом.

Ручная покупка того же символа (в приложении Binance, другим ботом или по API)
выглядит для агента как такая сделка. Отличить её от своего невидимого ордера агент
не может, поэтому вход остаётся UNKNOWN и повторно не отправляется. Это осознанный
консервативный выбор. Ошибочное освобождение стоило бы позиции на бирже без учёта и
без OCO, а удержание стоит только занятого резерва.

Само это состояние не пройдёт: ручная сделка остаётся в недавней истории символа,
которую читает агент.

### Профилактика

Аккаунт выделен под агента (§9.6): вручную на нём не торгуют. Особенно нельзя
покупать символ, по которому у агента есть вход в `unknown` или `submitted`.

### Действия

1. Ничего не покупать и не продавать по символу. Вход вручную не повторять.
2. Взять client id из алерта и найти его в истории ордеров Binance:
   Orders → Order History, либо `GET /api/v3/order?symbol=<SYMBOL>&origClientOrderId=<id>`.
3. **Ордер найден** — это вход агента. Ничего не трогать: как только биржа отдаст
   ордер по запросу, агент сам проведёт его (позиция, OCO либо освобождение при
   `EXPIRED`). Агент спрашивает биржу каждый раунд исполнения. Если ордер виден на
   бирже, а алерт держится несколько минут, передать разработчику client id и вывод
   запроса.
4. **Ордера нет**, а BUY-сделка из `foreign_trades` принадлежит ордеру без префикса
   `mta-`, значит вход не размещался и сделка ручная.
   - Ручную покупку убрать, как решит владелец: продать или вывести. Divergence по
     балансу снимется, когда следующая проверка его не найдёт.
   - Сам UNKNOWN-вход агент не освободит. Освободить его можно командой
     `release_entry`. В UI: страница Strategy → карточка «Unresolved entry» (она
     видна, пока висит алерт `unknown`; client id подставлен из алерта) → «Release
     entry» → подтвердить. Через API: `POST /api/v1/trading/commands/` с телом
     `{"type": "release_entry", "payload": {"client_order_id": "<id из алерта>"}}`.
     Агент сам проверяет, что ордера нет: запрос старше `recvWindow` + 60 с,
     биржа не знает client id, у каждой непонятной BUY-сделки после попытки ордер
     с чужим client id (не `mta-`) — история читается вся, от времени попытки,
     постранично, — и баланс базового актива сверх открытых позиций и этих чужих
     сделок меньше количества входа (сделка, которую биржа ещё не показывает,
     видна в балансе). Только тогда intent освобождается с причиной
     `released_by_operator`, а алерт `unknown` снимается. Любое сомнение даёт отказ
     `not released: <причина>`, и ничего не меняется. Отказ «too recent» значит
     повторить позже. «is on the exchange» — вернуться к шагу 3. «cannot identify
     order» или «may be ours» — ордер может быть нашим: передать разработчику
     client id и текст отказа. «may have filled» — на балансе есть столько актива,
     сколько купил бы вход, и чужие сделки этого не объясняют: либо вход исполнен,
     а биржа ещё не показывает его сделку, либо актив пришёл не сделкой (перевод).
     Повторить позже; если держится — передать разработчику.

## 2. Откат на ревизию без исполнителя (T0 и всё до `e133313`)

### Симптом

- Нужно откатить сервер на ревизию, в которой нет исполнения ордеров, например на T0
  `567f4f8` (`docs/DEPLOY.md` §6).
- `deploy.sh --revision <цель>` падает на шаге `(2a) барьер исполнения` с
  `откат на <цель> запрещён`, а в логе выкладки есть строки
  `barrier: unfinished execution <account>/<network>: positions=… intents=… attempts=…`.

### Почему так

Stop закрывает только admission: остановленный движок продолжает вести реальные
позиции (OCO, trailing, выход по времени, guard) и разрешать UNKNOWN-входы. Признаки
барьера доставки (`succeeded`, `lag = 0`, `pending = 0`, `idle`) выполняются и при
открытой позиции. В ревизии без исполнителя этого делать некому: OCO на бирже может
остаться, но позицию никто не сопровождает. БД агента при откате не меняется, поэтому
записи сохраняются, но работа по ним останавливается.

Незавершённая работа — то же, что считает `ExecutionRuntime.unfinished`, во всех
контекстах (аккаунт и сеть): позиция не в `closed`, intent в `reserved`, `submitted`
или `unknown`, попытка ордера в `prepared`, `sent` или `unknown`.

### Что делать

1. Не откатывать. Прежний агент уже поднят снова, флаг `trading:start_fence` стоит.
2. Проверить самому: `$COMPOSE exec -T agent python -m agent.execution.barrier`.
   Код 0 значит, что работы нет. Код 1 выводит список. Код 2 значит, что БД агента
   не прочитана: это не доказательство, откат запрещён.
   Если работает уже агент цели (прежний откат упал после `up`), модуля барьера в
   нём нет — тогда ответ даёт повторный `deploy.sh`: на шаге (2a) он спрашивает образ
   `releases/current`, у которого исполнитель есть.
3. Довести работу до конца текущей ревизией:
   - позиции закроются сами по OCO, trailing или выходу по времени (до 8 ч); раньше
     их можно закрыть командой `close_position` (§6, «Как закрыть позицию вручную»);
   - UNKNOWN-вход разрешится сам, когда биржа ответит; ручной случай описан в §1;
   - если `intents` или `attempts` держатся без алерта `unknown`, передать разработчику
     вывод барьера: откат до их разрешения запрещён.
4. Когда барьер даёт код 0, повторить откат по `docs/DEPLOY.md` §6 с шага 1. После
   Stop новой работы не появляется, поэтому код 0 окончателен.

## 3. Включить или выключить реальные сделки

Реальные сделки включаются отдельным переключателем владельца. Выбор сети и Start
их не включают и не выключают (ClickUp 869fgqxah, план §4.3).

### Где

UI: страница Strategy, карточка «Real trading». API: `POST /api/v1/trading/execution/`
с телом `{"settings": {"enabled": true, ...лимиты}}`. Текущее желаемое состояние —
`GET /api/v1/trading/execution/`, фактический режим агента — `actual.execution.mode`
в `GET /api/v1/trading/status/` (`off`, `enabled`, `paused(<причина>)`).

### Включить

1. Проверить, на какой сети работает стратегия: в диалоге включения она названа
   (на LIVE — «with real money»).
2. Проверить лимиты в блоке «Limits»: `max_symbols`, `slot_quote`, `position_share`,
   `daily_losing_trades_limit`, `max_slippage_pct` и остальные.
3. Включить и подтвердить. Watchdog агента (раз в 5 с) берёт lock и начинает
   сверку с биржей. Сверка проверяет каждый актив на счёте и может занять минуты:
   на testnet с ~490 тестовыми активами — около 150 с (ClickUp 869fgqu5u). Пока
   она идёт, режим — `paused(no_execution_lock)`, входы закрыты, а Start ждёт её
   окончания.
4. Включение при работающей стратегии не на USDT backend отклоняет сразу (422),
   и оно не сохраняется. Start не на USDT при включённых сделках тоже получает 422. Если агент всё же откажет (например, БД агента не мигрирована),
   причина видна в результате команды на карточке, а агент остаётся в режиме
   `off`. В сохранённых настройках при этом стоит ON, и при рестарте агент
   попробует применить их снова. Чтобы этого не было, выключите переключатель.
   Если при boot сохранённое ON несовместимо со стратегией, которую агент
   поднимает (не USDT), стратегия поднимается, сделки остаются выключены, а в
   heartbeat появляется алерт `settings`.

### Выключить

Выключение подтверждения не требует. Команда выключения встаёт в очередь за
Start/Stop и может ждать текущий Start. Чтобы немедленно остановить новые входы,
сначала нажмите «Pause entries»: эта команда выполняется вне очереди.
После выключения новые входы прекращаются сразу. Открытые
позиции, их защита и выходы продолжают сопровождаться. Lock агент отпускает,
только когда незавершённой работы не осталось.

Пауза («Pause entries») только приостанавливает новые входы до «Resume entries» и
не переживает рестарт агента. Переключатель рестарт переживает: он хранится в
`agent:execution`.

## 4. Права ключа и торговые группы Binance

### Как Binance описывает права

- **Права аккаунта** — поле `permissions` в `GET /api/v3/account`. Обычный
  spot-аккаунт получает `SPOT`. Аккаунт в торговой группе Binance получает
  вместо `SPOT` только имя группы, например `TRD_GRP_072`. Это нормально, а не
  отказ прав. Группа может смениться без нашего участия.
- **Права символа** — поле `permissionSets` в `GET /api/v3/exchangeInfo`. Это
  список наборов. Аккаунт может торговать символом, если у него есть хотя бы
  одно право **из каждого** набора (И по наборам, ИЛИ внутри набора). Старое
  поле `permissions` у символа Binance больше не заполняет; агент читает его,
  только если `permissionSets` нет.
- Подробности: [Spot API CHANGELOG](https://developers.binance.com/docs/binance-spot-api-docs/CHANGELOG)
  и [Spot testnet CHANGELOG](https://developers.binance.com/docs/binance-spot-api-docs/testnet/CHANGELOG).

Пример: `permissionSets=[["SPOT","TRD_GRP_072","TRD_GRP_073"]]` разрешает
аккаунту с `permissions=["TRD_GRP_072"]` торговать символом. Набор без 072 его
запрещает.

На 2026-10-16 live-аккаунт имеет `permissions=["TRD_GRP_072"]`, `canTrade=true`.
Группа 072 разрешена на 510 из 511 USDT-пар. Не разрешена RWUSDUSDT.

### Что проверяет агент

1. **Ключ** — при старте runtime и раз в 5 минут (`ACCOUNT_CHECK_EVERY`):
   `canTrade=true` и непустые `permissions`. `SPOT` не требуется. Если
   проверка не прошла, в heartbeat появляется алерт `key`:
   `API key cannot trade spot (canTrade=…, permissions=[…])`. Пока он висит,
   новые входы закрыты (fail-closed). Выходы и защита открытых позиций
   продолжают работать.
2. **Символ** — на каждом входе (`check_symbol` в `agent/agent/execution/sizing.py`):
   права аккаунта сверяются с `permissionSets` символа. Если символ не
   разрешён, вход отклоняется без ордера. В `execution_intent` он получает
   `state=REJECTED` и `reason=symbol_not_permitted`, а в деталях — права
   аккаунта и символ.

Список символов стратегии права не фильтруют: скрининг идёт по всем символам, а
отказ происходит только при попытке входа.

### Как проверить вручную

Права аккаунта (подписанный запрос, ключи из окружения агента; на сервере —
из каталога `releases/current`):

```bash
docker compose exec agent python -c "
import asyncio
from agent.exchange.rest import ExchangeRest
a = asyncio.run(ExchangeRest.connect('live').account())
print('canTrade', a.can_trade, 'permissions', a.permissions)"
```

Наборы прав символа (без ключа):

```bash
curl -s 'https://api.binance.com/api/v3/exchangeInfo?symbol=BTCUSDT' \
  | jq -c '.symbols[0].permissionSets'
```

Какие торгуемые USDT-пары закрыты для группы (подставьте свою; та же логика,
что в агенте: право из каждого набора):

```bash
curl -s 'https://api.binance.com/api/v3/exchangeInfo' | jq -r --arg g TRD_GRP_072 '
  .symbols[] | select(.quoteAsset=="USDT" and .status=="TRADING")
  | select(any(.permissionSets[]; index($g) == null)) | .symbol'
```

### Действия

- **Алерт `key` с `canTrade=false` или пустыми `permissions`.** Ключ или аккаунт
  ограничены на стороне Binance. Проверьте ключ в кабинете Binance: должна быть
  включена Spot Trading, IP сервера должен быть в whitelist. Без этого не
  включайте реальные сделки. Алерт снимается сам при следующей проверке (до
  5 минут) или при рестарте агента.
- **Много `symbol_not_permitted`.** Скорее всего, Binance перевела аккаунт в
  другую группу. Сравните `permissions` аккаунта с `permissionSets` отклонённых
  символов. Код менять не нужно: агент сверяет права на каждом входе.
- **Единичный `symbol_not_permitted`.** Символ закрыт для группы аккаунта (как
  RWUSDUSDT). Действий не нужно; при желании уберите символ из списка
  стратегии.

## 5. Недоступны БД, Redis или биржа

Общее правило: агент не угадывает. Чего он не может доказать, того не
делает, а входы закрывает. Ордер, исход которого неизвестен, повторно не
отправляется: агент выясняет его у биржи, когда связь вернётся.

### 5.1 БД (`mentis-db-1`)

Одна БД Postgres на backend (`app`) и агента (`agent`). Lock исполнения — advisory
lock на отдельном соединении с БД агента.

**Симптом.**
- Алерт `lock: execution lock lost; mutations stopped` и/или
  `database: cannot read execution state: …`, режим `paused(database)` или
  `paused(lock)`. В логе `execution lock lost …`, `execution round failed`.
- UI и API отвечают 503 «the database is unavailable» или не открываются.
- Если БД была недоступна при **старте** агента — алерт
  `schema: agent database not migrated; real execution closed`.

**Что делает агент.**
- Потеря соединения снимает lock. Пока lock не взят снова и не пройдена сверка
  с биржей, агент **ничего** не отправляет и не отменяет: ни входов, ни новых
  OCO, ни продаж.
- OCO, уже стоящие на бирже, продолжают защищать позиции: биржа исполнит стоп
  или тейк без агента.
- Не работают: trailing (стоп не подтягивается), выход по времени, guard,
  первая защита позиции, если вход исполнился прямо перед сбоем. Такая позиция
  остаётся без OCO, пока БД не вернётся.
- Когда БД вернулась, watchdog (раз в 5 с) сам берёт lock, проводит сверку с
  биржей и продолжает. Перезапуск не нужен.
- Исключение: если БД была недоступна **при старте** агента (алерт `schema`),
  исполнение закрыто до перезапуска агента.

**Действия.**
1. `$COMPOSE ps` и `$COMPOSE logs --since 30m db`: контейнер жив, нет ли
   ошибок диска или памяти (`df -h`, `free -m`).
2. Поднять БД: `$COMPOSE up -d db`. Ждать `healthy` в `$COMPOSE ps`.
3. Проверить heartbeat (§0): `lock` и `database` должны уйти в течение минуты.
4. Если висит `schema` — перезапустить агента: `$COMPOSE restart agent`.
5. Если сбой был дольше 30 с при открытой позиции без OCO — после восстановления
   появится `overdue:<SYMBOL>`; агент сам защитит или продаст остаток (§6.3 плана).
   Проверьте, что алерт ушёл.

### 5.2 Redis (`mentis-redis-1`)

Redis — только канал управления между backend и агентом: команды, heartbeat,
переключатель реальных сделок (`agent:execution`), снимок запуска стратегии
(`agent:runtime`). Позиции и ордера в Redis не хранятся.

**Симптом.**
- UI показывает «Offline / stale», команды отвечают 503 «Redis is unavailable».
- В логе агента `command stream error: …; retrying`,
  `cannot publish heartbeat (Redis unavailable)`.

**Что делает агент.**
- Исполнение продолжается: входы по сигналам стратегии, защита, выходы — им
  Redis не нужен. Последний включённый режим остаётся в памяти агента.
- Команды (Start/Stop, переключатель, пауза, `close_position`) до агента не
  доходят, backend отвечает 503. Агент пробует читать поток команд каждые 2 с;
  команды, принятые до сбоя, он дочитает после восстановления, если Redis не
  потерял данные (см. ниже).
- Если агент **перезапустится**, пока Redis недоступен, переключатель не
  прочитается: реальные сделки будут выключены (алерт `settings`), пока владелец
  не включит их снова.

**Действия.**
1. Если нужно срочно остановить входы, а UI не работает: остановить агента
   (`$COMPOSE stop agent`). Открытые позиции останутся под OCO на бирже, но без
   trailing и выхода по времени — поднимите агента, как только Redis вернётся.
2. `$COMPOSE ps`, `$COMPOSE logs --since 30m redis`; поднять: `$COMPOSE up -d redis`.
3. Проверить heartbeat (§0) и режим реальных сделок в UI.

**Данные Redis.** Redis пишет в именованный том `mentis_redis-data` журнал AOF
(`appendfsync everysec`) и снимок RDB при остановке. `restart`, `up -d` и
`$COMPOSE down` с последующим `up` данные сохраняют: переключатель реальных
сделок, снимок запуска и поток команд переживают их. При падении хоста
теряется не больше последней секунды записей. Данные пропадут только с
`$COMPOSE down -v` или удалением тома — так не делать. Если данные всё же
потеряны — агент поднимется с выключенными реальными сделками и без стратегии:
заново запустить стратегию и включить реальные сделки из UI (§3).
Стек, где Redis ещё писал в анонимный том, переводится на именованный при
выкладке (шаг (3a), `docs/DEPLOY.md` §2). **Исключение — откат на ревизию без
тома** (до 869fjdy14): там `$COMPOSE down` + `up` поднимает Redis на пустом
анонимном томе, `down` до следующей выкладки не делать; восстановление —
`docs/DEPLOY.md` §7 п. 3.

### 5.3 Биржа (Binance)

**Симптом.**
- В логе `Binance REST call failed`, `reconcile trades of … failed`,
  `account check failed`, `market streams connection lost … reconnecting`.
- Алерты `feed:<SYMBOL>: no recent trades`, `guard:<SYMBOL>`, через 120 с —
  `unknown: order mta-… outcome unknown for …s; not retried`; при открытой
  позиции без OCO через 30 с — `overdue:<SYMBOL>`.

**Что делает агент.**
- Запрос, который мог дойти до биржи (timeout, 5xx, `-1006`/`-1007`, обрыв),
  получает исход UNKNOWN и **не повторяется**. Вход в UNKNOWN держит резерв и
  слот и закрывает новые входы (`unknown_entry`), пока агент не найдёт ордер
  на бирже или не докажет его отсутствие.
- OCO, стоящие на бирже, работают и без агента.
- Websocket-потоки переподключаются сами с нарастающей паузой и догружают
  пропущенные свечи. Пока данных нет, trailing не двигает стоп, guard не
  действует (алерт `guard:`), выход по времени и аварийная продажа ждут
  котировку не старше 10 минут.
- Стратегия может перестать давать сигналы (нет свечей) — это видно в её
  сообщении, на исполнение не влияет.

**Действия.**
1. Проверить, что это биржа, а не сеть сервера:
   `curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://api.binance.com/api/v3/ping`
   (с сервера и с другой машины) и [статус Binance](https://www.binance.com/en/support/announcement).
2. Если идут работы биржи с объявленным временем — заранее нажать «Pause
   entries» (§3) и снять паузу после.
3. Ничего не делать с ордерами вручную: после восстановления агент сам
   разрешит UNKNOWN, проведёт сверку и защитит позиции. Через 5–10 минут после
   восстановления алерты `unknown`, `overdue:`, `feed:` должны уйти.
4. Если `unknown` держится дольше 10 минут после восстановления связи —
   разобрать по §1 (шаги 2–3) и §9.

## 6. HALT или делистинг символа с открытой позицией

### Как это выглядит на бирже

`exchangeInfo` отдаёт статус символа: `TRADING`, `HALT`, `BREAK` и др. Вне
`TRADING` новые ордера не принимаются. Перед делистингом Binance публикует
объявление (обычно за 1–2 недели); в API даты делистинга нет. В момент
делистинга биржа отменяет открытые ордера символа, затем символ пропадает из
`exchangeInfo`. Символы под наблюдением биржи (тег Monitoring) агент помечает
в списке символов UI — это кандидаты на делистинг.

### Что делает агент

- **Новые входы**: символ не в `TRADING` отклоняется с `symbol_not_trading`.
  Правила символа кешируются до 1 часа, поэтому в первый час остановки вход
  может уйти на биржу и получить отказ — без последствий, резерв
  освобождается.
- **Позиция под OCO**: OCO остаётся на бирже. Пока торгов нет, его ноги не
  исполнятся; при возобновлении торгов стоп может исполниться с проскальзыванием
  (гэп).
- **Выход по времени, trailing или `close_position` во время HALT**: OCO не
  снимается. Перед отменой OCO агент заново читает статус символа из
  `exchangeInfo`. Если символ не в `TRADING`, операция не начинается: OCO
  остаётся на бирже, в heartbeat — информационный алерт `halted:<SYMBOL>`
  («protection kept on the exchange, exits wait for trading»). Входы по другим
  символам он **не** закрывает. Выход по времени и trailing повторяются каждый
  круг и выполнятся сами, когда символ снова в `TRADING`; алерт снимется.
  `close_position` во время остановки отклоняется с сообщением
  `<SYMBOL> is HALT: not closed, its protection stays on the exchange`.
  Известную остановку агент перепроверяет не чаще раза в 60 с, поэтому выход
  может начаться до минуты позже возобновления торгов.
- **Статус символа не читается** (ошибка `exchangeInfo`): OCO тоже не
  снимается, выход ждёт с причиной `<SYMBOL> status unknown: list kept`,
  `close_position` отклоняется с `status of <SYMBOL> unknown: …`. В heartbeat —
  информационный алерт `status_unknown:<SYMBOL>` с текстом ошибки; входы по
  другим символам он не закрывает. Алерт снимается при первом успешном чтении
  статуса (тогда выход выполнится или сменится на `halted:<SYMBOL>`), при
  закрытии позиции и при выходе из контекста. Если он держится дольше
  нескольких минут — проверить доступность Binance с сервера
  (`curl -s 'https://api.binance.com/api/v3/exchangeInfo?symbol=<SYMBOL>' | jq -r '.symbols[0].status'`)
  и алерты бюджета веса (§7).
- **Операция, записанная до остановки**: если операция (выход или перенос стопа)
  записана, но отмена OCO ещё не отправлялась, агент отзывает её (событие
  `operation_withdrawn`) — позиция снова `protected`. Если отмена уже ушла на
  биржу, назад пути нет: позиция без OCO до возобновления торгов,
  `overdue:<SYMBOL>` и закрытые входы; при возобновлении агент продаст остаток.
- **После делистинга**: биржа отменила OCO, символа в `exchangeInfo` больше нет.
  Сверка увидит, что список не активен, и снимет с позиции статус
  `protected`, но ни доказать остаток, ни защитить, ни продать его агент не
  сможет. Алерт `overdue:<SYMBOL>` и закрытые входы останутся, пока владелец
  не спишет позицию командой `write_off_position` (ниже).

### Действия

**Есть объявление о делистинге символа с открытой позицией.**
Закрыть позицию вручную, пока символ в `TRADING`, и не откладывать на последний
день. Это единственный чистый путь.

**Как закрыть позицию вручную.** В UI кнопки нет, только API: `POST
/api/v1/trading/commands/` с телом
`{"type": "close_position", "payload": {"symbol": "<SYMBOL>"}}` (нужен токен
суперпользователя). Агент отменит OCO, докажет остаток
и продаст его по рынку; позиция закроется с причиной `manual`. Результат — в
`GET /api/v1/trading/commands/{id}/state/`. Продавать через приложение Binance
нельзя: агент увидит чужую сделку, позиция останется открытой, а баланс
разойдётся (divergence, §9).

**Символ в HALT или BREAK, позиция под OCO.**
1. Не закрывать позицию и не трогать OCO: на остановленном рынке это только
   снимет защиту.
2. Проверить статус:
   `curl -s 'https://api.binance.com/api/v3/exchangeInfo?symbol=<SYMBOL>' | jq -r '.symbols[0].status'`.
3. Ждать возобновления. Выход по времени, наступивший во время остановки,
   агент отложит (`halted:<SYMBOL>`) и выполнит после возобновления торгов.
   `overdue:<SYMBOL>` здесь означает, что отмена OCO ушла до остановки, — см.
   «Что делает агент».

**Символ уже делистингован, позиция осталась.**
1. Входы закрыты алертом `overdue:<SYMBOL>` — это правильно, не обходить.
2. Узнать у Binance, что стало с активом (конвертация, вывод). Решение по
   активу — владельца.
3. Списать позицию командой `write_off_position` (только API, нужен токен
   суперпользователя): `POST /api/v1/trading/commands/` с телом
   `{"type": "write_off_position", "payload": {"symbol": "<SYMBOL>", "confirm": "<SYMBOL>", "proceeds_quote": "<сумма>"}}`.
   - `confirm` повторяет символ — защита от опечатки.
   - `proceeds_quote` — сколько котируемой валюты (USDT) владелец получил за
     актив (конвертация Binance); `0` или без поля, если ничего.
   - Агент закрывает позицию в БД без ордеров с причиной `delisted` /
     `write_off`, PnL = выручка − покупка − комиссии. Дата закрытия — момент
     списания, даже если часть позиции продана раньше: по ней считаются
     дневной лимит убыточных сделок (если результат убыточный) и cooldown
     символа. Снимаются
     `overdue:<SYMBOL>` и `halted:<SYMBOL>`, входы открываются.
   - Статус символа агент читает из `exchangeInfo` заново, кешу не верит.
     Отказ, если символ ещё в `TRADING` (тогда `close_position`), если статус
     не читается (повторить позже), если на бирже
     есть открытые ордера по символу (например, OCO при `BREAK` — сначала
     дождаться торгов или отменить вручную), или если у позиции есть ордер с
     невыясненным исходом (дождаться сверки). Причина — в
     `GET /api/v1/trading/commands/{id}/state/`.

## 7. Ответы 429 и 418 от Binance

### Как это устроено

Binance ограничивает вес запросов на **IP** (6000 в минуту на spot) и число
ордеров. Превышение — HTTP 429 с `Retry-After`. Если продолжать слать запросы
после 429, биржа банит IP: HTTP 418, от 2 минут до 3 дней, срок растёт при
повторах.

Агент ведёт один бюджет веса на сеть для всех своих REST-запросов и сверяет его
с заголовком `X-MBX-USED-WEIGHT-1M`. Доли лимита по приоритетам: защита и
выходы — до 100%, сверка — до 90%, входы — до 75%, рыночные данные стратегии —
до 60%. Запросы по веб-сокетам в бюджет не входят.

### Что делает агент

- **429**: все REST-запросы агента ждут до `Retry-After` (60 с, если заголовка
  нет). Запрос сам за вызывающего не повторяется. Вход, получивший 429,
  освобождается с причиной `entry_rate_limited:<код>`.
- **418**: до конца бана каждый запрос сразу получает отказ, ничего не
  отправляется. Входы закрыты (`paused(ip_banned)`). Защита не
  гарантируется: биржа не примет ни OCO, ни продажу. OCO, уже стоящие на
  бирже, работают.
- Ни 429, ни 418 не дают UNKNOWN: биржа запрос не исполняла.

### Симптом

- В логе `rate_limited`, `banned`, `TooManyRequests`, `RateLimitBan`,
  `request weight not available`, `IP banned by the exchange (418)`.
- В `execution_intent` причины `entry_rate_limited:…` / `entry_banned:…`.
- Режим `paused(ip_banned)`.

### Действия

1. **Ничего не перезапускать в цикле.** Рестарт агента сбрасывает его счётчик,
   и новый процесс снова начнёт слать запросы в бан — это продлевает бан.
2. Узнать, кто ещё ходит на Binance с того же внешнего IP: другие боты и
   скрипты на сервере и в той же сети, вторая копия агента (`docker ps`,
   `$COMPOSE ps` — контейнер агента должен быть один). Остановить лишнее.
3. При 418: дождаться конца бана (`Retry-After` в логе, секунды). Новые входы
   откроются сами. Если в бан попала позиция без OCO — после бана агент сам её
   защитит или продаст (`overdue:` до этого).
4. Если 429 повторяются без внешних причин — передать разработчику лог за
   час: значит, оценка веса агента расходится с биржевой.

## 8. Рассинхрон часов

### Как это устроено

Подписанный запрос несёт время сервера. Binance отклоняет его с `-1021`
(«Timestamp for this request is outside of the recvWindow»), если время
расходится больше чем на `recvWindow` (у агента 5 с) или опережает биржу больше
чем на 1 с. Контейнеры берут время хоста; на сервере (AlmaLinux) время
синхронизирует `chronyd`.

Агент меряет расхождение с биржей при подключении и затем раз в час:

- больше 1 с — алерт `clock_warning: clock off by …s`, входы открыты;
- больше 2,5 с (половина `recvWindow`) — алерт `clock: clock off by …s`,
  входы закрыты (`paused(clock)`).

### Симптом

- Алерт `clock` или `clock_warning`.
- В `execution_intent` причины `entry_rejected:-1021`, в логе `-1021`.
  Защита и продажа с `-1021` ждут и повторяются следующими раундами.

### Действия

1. На хосте: `timedatectl` (должно быть `System clock synchronized: yes`,
   `NTP service: active`) и `chronyc tracking` (`System time` — смещение).
2. Если синхронизации нет: `sudo systemctl restart chronyd`, затем
   `sudo chronyc makestep` (разовый шаг времени) и снова `chronyc tracking`.
   Проверить, что с сервера доступны NTP-источники (`chronyc sources`).
3. Агент перепроверяет время раз в час. Чтобы алерт снялся сразу —
   `$COMPOSE restart agent` (переключатель и позиции переживают рестарт).
4. Если время хоста верное, а алерт держится: сравнить с биржей
   `curl -s https://api.binance.com/api/v3/time` и `date +%s%3N` — большая
   сетевая задержка тоже даёт смещение. Передать разработчику оба значения.

## 9. Ручная сверка с историей ордеров Binance

Нужна, когда есть divergence, `foreign_trades:`, `quarantine:`, затяжной
`unknown` или сомнение, что учёт агента совпадает с биржей. Агент сам сверяется
с биржей при взятии lock и каждые 60 с (`reconcile_interval_s`); ручная сверка
— проверка оператора, она ничего не меняет.

### Как агент называет свои ордера

Все ордера агента имеют client id `mta-<24 hex от signal_id>-<роль><номер>`:
`e` — вход (BUY LIMIT FOK), `pl` — OCO-список, `pt` — нога тейк-профита,
`ps` — нога стопа, `x` — продажа по рынку. Ордер без префикса `mta-` агент не
ставил. Ордер с `mta-`, которого нет в БД агента, — карантин (`quarantine:`):
агент его не трогает.

### Шаг 1. Что записал агент

```sql
-- psql: docker exec -it mentis-db-1 psql -U postgres -d agent
-- Позиции символа за период
select id, status, quantity, bought_qty, sold_qty, fill_vwap, realized_pnl,
       outcome->>'reason' as reason, opened_at, closed_at
from position
where symbol = 'BTCUSDT' and created_at >= '2026-10-16'
order by created_at;

-- Ордера агента и их исходы
select client_order_id, state, exchange_status, order_id, executed_qty,
       error->>'message' as error, created_at
from order_attempt
where symbol = 'BTCUSDT' and created_at >= '2026-10-16'
order by created_at;

-- Сделки в учёте агента
select trade_id, order_id, client_order_id, side, quantity, price,
       commission, commission_asset, trade_time, source
from fill
where symbol = 'BTCUSDT' and trade_time >= '2026-10-16'
order by trade_id;
```

### Шаг 2. Что есть на бирже

Только чтение, ключ из окружения агента. Аргументы: сеть, символ, сутки (UTC):

```bash
$COMPOSE exec -T agent python - live BTCUSDT 2026-10-16 <<'PY'
import sys
from datetime import UTC, datetime, timedelta
from agent.exchange.rest import ExchangeRest

network, symbol, day = sys.argv[1:4]
start = datetime.fromisoformat(day).replace(tzinfo=UTC)
window = {
    "start_time": int(start.timestamp() * 1000),
    "end_time": int((start + timedelta(days=1)).timestamp() * 1000) - 1,
}
api = ExchangeRest.connect(network)._client.rest_api
names = {}
for o in api.all_orders(symbol=symbol, limit=1000, **window).data():
    names[o.order_id] = o.client_order_id
    print("order", o.order_id, o.client_order_id, o.side, o.type, o.status,
          o.executed_qty, datetime.fromtimestamp(o.time / 1000, UTC).isoformat())
for t in api.my_trades(symbol=symbol, limit=1000, **window).data():
    print("trade", t.id, t.order_id, names.get(t.order_id, "?"),
          "BUY" if t.is_buyer else "SELL", t.qty, t.price, t.commission,
          t.commission_asset, datetime.fromtimestamp(t.time / 1000, UTC).isoformat())
PY
```

`?` в сделке — ордер выставлен вне этих суток (сделка ордера прошлого дня) или
не найден; уточните соседний день. Вес запросов — 20 + 20 на сутки, не
запускайте в цикле на много символов (§7).

### Шаг 3. Сравнить

| На бирже | В БД агента | Что значит |
|---|---|---|
| ордер `mta-…`, сделки | `order_attempt` и `fill` с теми же `order_id`/`trade_id` | норма |
| сделка ордера `mta-…` | нет `fill` | сверка ещё не прошла или отстала; подождать 1–2 мин, затем к разработчику |
| ордер `mta-…` | нет `order_attempt` | карантин (`quarantine:`), к разработчику |
| `order_attempt` в `unknown` | ордера нет | §1 (UNKNOWN-вход) |
| ордер или сделка без `mta-` | — | ручная торговля на аккаунте агента (§9.6 плана): divergence, решает владелец |
| баланс актива | нет открытой позиции | divergence по балансу: продать/вывести по решению владельца |

Сумма `quantity` в `fill` по позиции должна совпасть с `executed_qty` её
ордеров, а `bought_qty - sold_qty` открытой позиции — с балансом актива на бирже
(за вычетом комиссий в базовом активе и пыли). Расхождение, которое не
объясняет таблица выше, — к разработчику: id позиции, client id ордеров и вывод
обоих шагов.
