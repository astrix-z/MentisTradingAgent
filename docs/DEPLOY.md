# Эксплуатация live/testnet-стенда

> Как устроен стенд на выделенном хосте, как выкладывать обновления, как
> восстанавливаться после сбоя. Стенд закрыт от интернета — доступен только из
> локальной сети 192.168.55.0/24 (firewalld пропускает 8010/tcp с этой
> подсети). Разработка ведётся на машине разработчика — на сервере крутится
> только длительный прогон (`docs/TRIPPLE_SCREEN_WORKING PROCESS.md`).

---

## 1. Архитектура

```
машина разработки                        сервер 192.168.55.40 «docker-host» (jb, группа docker)
┌──────────────────────────┐    ssh     ┌────────────────────────────────────────────────┐
│  git (репозиторий)       │ ─────────► │  стек docker compose «mentis»:                 │
│  ./scripts/deploy.sh     │            │    db       postgres:18 (volume, без порта)     │
│  .env  (секреты dev)     │            │    redis    redis:7 (без порта)                 │
└──────────────────────────┘            │    backend  FastAPI+SPA :8000 → 0.0.0.0:8010    │
                                        │    agent    без портов, торгует через Binance API│
                                        │  ~/apps/mentis-trading-agent   код (.env.prod)   │
                                        │  ~/backups/mentis-trading-agent/  дампы БД       │
                                        │  рядом (чужое, не трогать): plan-oplat, n8n,     │
                                        │  nginx-proxy-manager (80/81/443), postgres-shared │
                                        │  (5432) — порты заняты, поэтому наш db/redis без  │
                                        │  портов, backend — на непересекающемся 8010       │
                                        └────────────────────────────────────────────────┘
                    LAN 192.168.55.0/24 ──► 192.168.55.40:8010 (firewalld rich rule,
                    источник ограничен подсетью; в интернет порт не смотрит)
```

- **Публикации в интернет нет, но открыт в локальной сети.** `backend`
  слушает на `${WEB_BIND:-0.0.0.0}:${WEB_PORT:-8010}` хоста (см.
  `compose.prod.yml`), а firewalld на 55.40 пропускает 8010/tcp **только** с
  источника `192.168.55.0/24` (rich rule в зоне `public` — команда в §3). Это
  live-trading с реальными деньгами — домен/Nginx Proxy Manager сознательно
  не заводили, в отличие от `plan-oplat` на этом же хосте. Доступ:
  ```
  http://192.168.55.40:8010   # с любой машины в 192.168.55.0/24
  ```
  Чтобы снова сузить доступ до одной машины: в `.env.prod` верните
  `WEB_BIND=127.0.0.1`, пересоздайте `backend` (`docker compose ... up -d`) и
  используйте `ssh -L 8010:localhost:8010 jb@192.168.55.40`.
- **`agent` без единого опубликованного порта** — так и в базовом
  `compose.yml`: UI обязан доставать его только через `backend`.
- **БД и Redis не публикуются.** Порт 5432 на хосте и так занят чужим
  `postgres-shared` — конфликта нет по конструкции, а не по счастливой
  случайности.
- **Обе БД агента создаются сами при старте**: `backend` запускает
  `prestart.sh` (Alembic + initial data) для базы `app`; `agent` создаёт свою
  базу `agent` сам при первом запуске (`ensure_settings_database`,
  идемпотентно). Отдельного шага инициализации не нужно.
- **`proxy` (Traefik) и `adminer`** остаются в профиле `extras` из
  `compose.yml` и не поднимаются обычным деплоем. `adminer`, если понадобится,
  — тоже только на loopback (`127.0.0.1:${ADMINER_PORT:-8011}`).

## 2. Регулярный деплой (основной сценарий)

Ветки: `development` — разработка (ветка по умолчанию, сюда идут PR), `stage` —
кандидат в выпуск, `production` — то, что работает на 55.40. Код поднимается
только вперёд: `development` → `stage` → `production`, merge через PR.
На 2026-10-06 `production` и `stage` стоят на `567f4f8` — ревизии, выложенной
2026-09-23 (`T0`, §3).

```sh
git switch production && git pull       # деплоится только то, что есть в origin/production
./scripts/deploy.sh                     # HEAD; --revision <rev> — откат на ревизию из истории production
```

Скрипт (по умолчанию `DEPLOY_SERVER=192.168.55.40`, `DEPLOY_USER=jb`) локально
только проверяет (SSH, ревизия не старше `608cfa1`, ревизия — вершина или предок
`production` в `origin` (`DEPLOY_REMOTE`/`DEPLOY_BRANCH`), linger — §3) и загружает файлы
**своей попытки**: артефакт ревизии в `~/apps/releases/stage-<попытка>/` и копию
`scripts/deploy-fence.sh` из текущего дерева. Всё остальное делает **скрипт ограды на
сервере** в юните пользователя `mentis-deploy` (`systemctl --user status mentis-deploy`),
поэтому обрыв SSH (сон ноутбука, VPN) выкладку не прерывает:

1. дампы `app` и `agent` в
   `~/backups/mentis-trading-agent/pre-deploy-<база>-<ревизия>-<дата>.dump`
   (последние 10 на базу; `--no-backup` — пропустить, не рекомендуется). Дамп
   пишется во временный файл и получает имя только целым; сбой или пустой дамп
   существующей базы останавливает выкладку до установки, базы, которой ещё нет,
   пропускаются;
2. проверки контракта цели (сервисы `backend`, `agent`, `redis`; образы
   `mentis-*:latest`) и сборка **сразу как** `mentis-*:<ревизия>` — `:latest` сборкой
   не сдвигается. Образы ревизии уже есть (откат) — без сборки. Всё это — из
   артефакта попытки, поэтому отказ здесь оставляет `~/apps/mentis-trading-agent`
   деревом работающей ревизии;
3. чистая установка ревизии в `~/apps/mentis-trading-agent` (файлы, которых нет в
   ревизии, удаляются; `.env.prod` сохраняется);
4. **окно G4** (план §4.6): (1) флаг `trading:start_fence` — Start по обоим маршрутам
   отвечает `503 "starting is closed for maintenance"`, Stop работает; (2) остановка
   агента; (3) удаление `agent:strategies`; (4) `:latest` → `:<ревизия>` и `up`;
   (5) ожидание каталога нового агента до 2 мин — каталогом считается только JSON
   с версией и непустым списком стратегий, чей `schema_hash` совпадает с sha256
   того, что хэширует агент цели (проверка — `python3` на сервере): с `e4dffb4` —
   стратегии и настройки исполнения (`execution`), у более ранних ревизий (от
   `608cfa1`, ключа `execution` нет) — только список стратегий; обрезанный или
   похожий текст флаг не снимает; healthcheck backend до 2 мин; затем каталог
   проверяет сам backend цели — его компилятор через `compose exec backend`
   (`compile_published`, а у ревизий до `a66a659`, где её нет, — разбор JSON и
   `compile_catalog`, как в их `read_catalog`): неподдерживаемая версия или
   негодная схема настроек флаг не снимает. Так откат на любую допустимую
   ревизию, включая T0, проходит G4;
   (6) снятие флага. Каждый вызов в ожиданиях ограничен по времени;
5. `~/apps/releases/current` и `history`, ротация образов (последние 10 ревизий по
   журналу; `releases/pinned` и `current` не удаляются) и файлов попыток (лог, код
   выхода и копия скрипта ограды — последние 20 завершённых; попытки без `.exit` не
   трогаются). Сбой здесь, уже после снятия флага, ставит флаг снова.

Лог и код выхода — `~/apps/releases/deploy-<ревизия>-<попытка>.log` и `.exit`;
`deploy.sh` показывает лог и ждёт код (до 60 мин, юнит при таймауте не
останавливается). Вторая выкладка той же ревизии подключается к идущей, другой
ревизии — отказывает, ничего не меняя.

Флаги: `--revision <rev>`, `--allow-dirty`, `--no-build`, `--no-backup`,
`--t0-revision <rev>` и `--t0-confirm` (первый запуск, §3).
Если пользователь на сервере не `jb`: `DEPLOY_USER=<имя> ./scripts/deploy.sh`.

**Деплой — окно, а не момент.** Пока идёт G4 (обычно столько же, сколько раньше
`up`), Start закрыт, а агент перезапускается. Идущая стратегия восстанавливается из
снапшота, как при любом рестарте. Не выкладывайте в момент, когда нужен Start.

**Сбой.** При сбое скрипт печатает, какие образы у backend и агента, и **оставляет
флаг** (Start закрыт; после (6) — ставит его снова): после остановки агента `trap`
поднимает прежнего, при сбое внутри `up` — агента из `releases/current` (а
`mentis-backend:latest` указывает на образ того backend, что реально работает), после
`up` агент цели работает. Сбой до шага (1) флага не ставит — `deploy.sh` так и пишет.
Остановка юнита (`systemctl --user stop mentis-deploy`) —
тоже сбой, не успех. Снять флаг — повторный `deploy.sh` или после проверки
`docker compose … exec -T redis redis-cli DEL trading:start_fence`.

**Деплой не останавливает торговлю и не запускает новую.** Флаг G4 запрещает только
**новые** Start. Если стратегия шла (`desired.running = true`), новый агент при старте
восстанавливает её из снапшота и продолжает торговать — как при любом рестарте.
Если не шла — агент сидит без сделок, пока кто-то явно не нажмёт «start». Чтобы
после выкладки торговли точно не было, до неё нужен Stop с барьером доставки
(§6, шаг 2): обычный `deploy.sh` его не делает.

## 3. Первоначальная настройка сервера (один раз)

```sh
ssh jb@192.168.55.40 'mkdir -p ~/apps/mentis-trading-agent'
scp .env.prod.example jb@192.168.55.40:~/apps/mentis-trading-agent/.env.prod
ssh jb@192.168.55.40 'chmod 600 ~/apps/mentis-trading-agent/.env.prod'
# затем на сервере: заполнить реальные значения в .env.prod (см. комментарии в файле)
./scripts/deploy.sh
```

`.env.prod.example` в git документирует все нужные переменные (порт/бинд,
секреты, Binance-ключи). Реальный `.env.prod` на сервере в git не попадает
(`.gitignore`) и `deploy.sh` его не трогает.

**Linger (один раз).** Скрипт ограды — юнит пользователя; без linger он умирает
вместе с SSH-сессией, поэтому `deploy.sh` без него отказывает:

```sh
ssh -t jb@192.168.55.40 'sudo loginctl enable-linger jb'
```

**Первый запуск нового `deploy.sh` (T0).** На сервере ещё нет `releases/current`, и
скрипт должен знать, какая ревизия работает сейчас, — это цель отката «до серии»:

```sh
./scripts/deploy.sh --t0-revision <ревизия, выкаченная последней>
```

Скрипт сверяет её с именем последнего `pre-deploy-app-<ревизия>-*.dump` и проверяет,
что работающие контейнеры на образах `mentis-*:latest` и хотя бы один из них создан
после дампа. Иначе — отказ; продолжить можно только с `--t0-confirm` после проверки
человеком. Затем образы работающих контейнеров помечаются `:<T0>`, и только после
обоих тегов T0 закрепляется в `~/apps/releases/pinned` (и `current`). Если второй тег
не поставился, первый остаётся (он указывает на работающий образ; снимать его опасно —
см. ниже), T0 не закрепляется, выкладка отказывает до G4; повторный запуск ставит оба
тега заново. Если образа работающего контейнера уже нет
(Docker с хранилищем containerd удаляет образ, у которого сборка забрала тег, даже под
работающим контейнером), T0 закрепить нечем — отказ, `--t0-confirm` не помогает. Его `uv.lock` из `APP_DIR` сохраняется только для справки
(`releases/<T0>.appdir.uv.lock`): происхождение этого файла не доказано, и
пересобрать T0 по нему скрипт не станет — T0 живёт на закреплённых образах.

Открыть порт `WEB_PORT` для локальной сети (нужен sudo на сервере — доступ
только по паролю в интерактивном `ssh -t`, не через чат-агента):

```sh
ssh -t jb@192.168.55.40 'sudo firewall-cmd --permanent --zone=public \
  --add-rich-rule="rule family=\"ipv4\" source address=\"192.168.55.0/24\" port protocol=\"tcp\" port=\"8010\" accept" \
  && sudo firewall-cmd --reload'
```

(Разово выполнено 2026-09-20 для порта 8010 — при смене `WEB_PORT` в
`.env.prod` повторить с новым портом.)

## 4. Наблюдение и отладка

На сервере (или через ssh):

```sh
cd ~/apps/mentis-trading-agent
docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml ps
docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml logs -f agent
docker exec -it mentis-db-1 psql -U postgres -d app     # или -d agent
docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml exec -T agent \
  cat /app/agent/logs/signals.log
```

Здоровье: `curl http://192.168.55.40:8010/api/v1/utils/health-check/` — с любой
машины в локальной сети (см. §1).

## 5. Бэкапы и восстановление

- **Перед каждым деплоем**: см. §2. Ручного планировщика (systemd-таймера) для
  ежедневных бэкапов пока нет — при необходимости завести по образцу
  `plan-oplat/scripts/server/backup-db.sh` на этом же хосте.

Восстановление (заменяет содержимое БД на момент дампа):

```sh
ssh jb@192.168.55.40
cd ~/apps/mentis-trading-agent
docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml stop backend agent
cat ~/backups/mentis-trading-agent/<файл>.dump | \
  docker exec -i mentis-db-1 pg_restore -U postgres -d app --clean --if-exists   # или -d agent
docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml start backend agent
```

## 6. Откат релиза (runbook G3)

Любой откат — только так (план §4.6 G3): откат может убрать поддержку текущей
конфигурации (например, `Fast`), а старый агент при старте восстанавливает
`desired` и дочитывает поток команд. Цели — только **реально выкатывавшиеся**
ревизии (`~/apps/releases/history`), у которых есть образы или tracked `uv.lock`.
`COMPOSE` ниже — `docker compose --env-file .env.prod -f compose.yml -f compose.prod.yml`
в `~/apps/mentis-trading-agent`.

**Откат — эксклюзивная операция.** Шаги 1–6 выполняются руками вне юнита
`mentis-deploy`, поэтому его мьютекс их не защищает: обычная выкладка, начатая в это
время, сняла бы флаг и подняла бы свою ревизию посреди downgrade. До шага 1:
`systemctl --user status mentis-deploy` — юнита нет; всех, кто может выкладывать,
предупредить, что до конца шага 8 выкладок нет. Шаг 7 — единственная выкладка.

1. **Флаг.** `$COMPOSE exec -T redis redis-cli SET trading:start_fence "rollback <кто> <когда>"`.
   С этого момента ни один Start не записывается, Stop и чтение работают.
2. **Stop и барьер доставки.** Stop через UI/API; дождаться: `GET
   /trading/commands/{id}/state/` этой Stop — `status = succeeded`; `$COMPOSE exec -T redis
   redis-cli XINFO GROUPS agent:commands:stream` — `lag = 0` и `pending = 0`;
   `GET /trading/status/` — `actual.state = idle`. Нужны все три: пока агент стоит,
   а Start ещё в потоке, статус показывает `idle` и `online = true` (срок heartbeat
   не истёк). Открытые позиции сопровождаются независимо от этого.
3. **Остановить backend:** `$COMPOSE stop backend` — backend цели может не знать флага.
4. **Записать параметры** из `desired` (`GET /trading/status/` до шага 3 или
   `redis-cli GET agent:runtime`) — это справка, не payload.
5. **Миграции.** Если у цели нет каких-то применённых миграций: дамп (§5), затем
   текущим образом `$COMPOSE run --rm backend alembic downgrade <ревизия alembic цели>`.
   Entrypoint образа сначала выполняет `prestart.sh` (`upgrade head` этого же образа —
   база уже на нём, изменений нет; в выводе будет «Initial data created»).
6. **Агент:** `$COMPOSE stop agent` и `redis-cli DEL agent:strategies`.
7. **Выкатить цель** с машины разработки текущим скриптом:
   `./scripts/deploy.sh --revision <ревизия>` (не `git checkout`: у старой ревизии
   старый скрипт). Он поставит уже стоящий флаг, поднимет цель на её сохранённых
   образах и снимет флаг после публикации каталога её агентом.
8. **Проверить:** `$COMPOSE exec backend alembic current` = ревизия цели; каталог
   опубликован её агентом (`redis-cli GET agent:strategies`); флаг снят.
9. **Start** с конфигурацией, которую принимает каталог цели (например, её `Default`).

Если миграция из нового релиза необратимо изменила данные, откат кода её **не**
отменяет — восстановите БД из `pre-deploy-*.dump` (§5).

Шаг 5 касается только БД `app`. `downgrade` за ревизию наборов (`c5d2e8f1a7b3`) удаляет
таблицы наборов и списков — сохранённые пользователями наборы пропадают, вернуть их можно
только из дампа шага 5. `downgrade` за `a7e3c1d9f5b2` удаляет `signal_exit_pending` — EXIT, ждущие
запоздавшую ENTRY; стратегия EXIT сейчас не публикует, таблица пуста. `downgrade` за
`f4b8c2d6e1a9` удаляет `signalposition.closed_by` (кто закрыл позицию: EXIT агента
или просмотр) — сами закрытия и цены остаются. БД `agent` не откатывается: агент до серии EXEC создаёт свои
таблицы `create_all` и новые таблицы (исполнение, `signal_watch`, `alembic_version`) не трогает; при
следующей выкладке новый агент продолжает миграции с записанной ревизии.

**Цели отката** (PRESET-09b) — только ревизии, реально выкатывавшиеся на сервер. На
2026-10-05 серия PRESET ещё не выкатывалась (`releases/` на сервере нет), поэтому цель одна:

| Цель | Ревизия | Alembic `app` | Имена полей | Правило ТФ | Наборы, таблицы | Start |
|---|---|---|---|---|---|---|
| `T0` | `567f4f8` (выкладка 2026-09-23; агент не менялся с `bef05d5`) | `b3f7a1c9d2e4` | `swing_low_h1_n`, `trail_m15_n` | `16:4:1` | нет | `Default` проходит, `Fast` → `422` по правилу ТФ |

`Fast` на `T0` подаётся в её именах и без полей, которых у неё нет (`trail_cap_pct`,
`max_hold_hours`): `1h / 15m / 5m`, `tp_pct 5`, `signal_validity_minutes 5`, остальное
как `Default` — отказ должен быть по `16:4:1` (`15m ≠ 4 × 5m`), а не по лишним ключам.
`T0` закрепляется первым запуском нового скрипта: `./scripts/deploy.sh --t0-revision 567f4f8`
(§3). `T1` (09a + 01–03 без 04+) и `T2` (04–06) появятся в таблице, только если их
выкатят отдельно; промежуточные коммиты development целями не являются.

**Репетиция 2026-10-05** (изолированный стенд: контейнер с systemd, sshd и своим Docker,
`DEPLOY_SSH`; история прода воспроизведена старым скриптом — `bef05d5`, затем `567f4f8`):

## 7. Правила и предостережения

1. **Один Binance live-ключ — один активный стенд.** Ключ перенесён с машины
   разработки на этот сервер (2026-09-20). **Никогда не запускайте
   live-стратегию на двух стендах одновременно с одним и тем же ключом** —
   Binance получит дублирующиеся ордера. Если нужно снова проверять
   стратегию локально live — сначала остановите её здесь (или наоборот).
2. **Секреты** — только в `.env` (машина разработки) и
   `~/apps/mentis-trading-agent/.env.prod` (сервер, права 600). В git не
   попадают.
3. **Деплоится только закоммиченное** (`--revision` — только ревизии из git). Ручные правки внутри контейнеров не
   переживут пересоздание — постоянное только через репозиторий (код) или
   volume (данные БД, `agent-signal-log`).
4. **Известная проблема ре-скрининга** (`_rescreen_loop` может умереть
   насовсем при транзиентной ошибке WS-подписки — ClickUp `869f4dqry`) ещё не
   исправлена на момент первого деплоя сюда. При длительном прогоне сверяйте
   `active symbols updated` в логе `agent`, не завис ли набор символов — см.
   `docs/TRIPPLE_SCREEN_WORKING PROCESS.md`.
5. Порт `WEB_PORT`/`ADMINER_PORT` должны быть свободны на 55.40 — там живут
   другие контейнеры (`plan-oplat`, `n8n`, `nginx-proxy-manager` на 80/81/443,
   `postgres-shared` на 5432). При конфликте — сменить в `.env.prod` **и**
   переоткрыть новый порт в firewalld (§3) — старое правило само не переедет.
6. **UI открыт всей локальной сети 192.168.55.0/24 без дополнительного
   пароля на уровне сети** — единственная защита на этом уровне — firewalld
   (источник ограничен подсетью) и логин в самом приложении
   (`FIRST_SUPERUSER`). Не подключать этот хост к недоверенным сетям/VPN, не
   меняя `WEB_BIND` обратно на `127.0.0.1`.
