 Собрал полную картину. Вот как ведёт себя TripleScreen после старта.
                                                                   
  Файлы стратегии
                                                                   
  agent/agent/strategies/tripple_screen/: strategy.py (528 строк,
  основная логика), indicators.py (математика индикаторов),
  settings.py (параметры), schema.py (ограничения для UI).
                                                                   
  Три «экрана» (Triple Screen — классика Элдера, адаптированная)
                                                                   
  Работают на трёх таймфреймах с жёстко навязанным соотношением
  16:4:1 (settings.py:91): tide (прилив, по умолчанию 4h), wave
  (волна, 1h), ripple (рябь, 15m).
                                                                   
  1. Tide — экран тренда (_tide, strategy.py:449-490)
  Тройной EMA по close, периоды (5, 13, 34) по умолчанию.
  Bullish-тренд признаётся, только если ВСЕ пять условий истинны:
  быстрая EMA растёт, средняя растёт, медленная растёт, быстрая > средней, последний close > медленной EMA. Если хоть одно ложно — 
  тренда нет, и весь сигнал глушится на этом этапе
  (strategy.py:370-371) — дальше даже не считается.
                                                                   
  2. Wave — экран осциллятора (_wave, strategy.py:498-527)
  Stochastic %K(5)/%D(3)/slowD(3) + Force Index Элдера (EMA(2) от
  (close[i]-close[i-1])*volume[i]). Разворот вверх (pullback_up)
  требует одновременно:
  - %K вышел из зоны перепроданности (был <20, стал ≥20),
  - %K пересёк %D снизу вверх,
  - Force Index пересёк ноль снизу вверх.
                                                                   
  3. Ripple — экран входа (_decide, strategy.py:369-378)
  Просто: close последней закрытой 15м-свечи пробивает high
  предыдущей 15м-свечи. 
  
  Логика гейтинга сигнала
                                                                   
  Порядок проверок (первая сработавшая причина блокировки
  становится reason): нет тренда → нет пуллбэка (wave) → нет пробоя
  (ripple) → уже есть позиция по символу → кулдаун (60 мин после
  закрытия) → эпоха уже отработана. Если всё пройдено —
  type="ENTRY", иначе type="HOLD" с причиной.
                                                                   
  Для ENTRY считаются: стоп (минимум low последних 2 wave-свечей
  минус 0.1%), тейк (+10% от входа), срок действия сигнала (15
  минут).
                                                                   
  Что происходит на каждой WS-свече (_on_kline,
  strategy.py:178-191)
                                                                   
  Прилетает каждое сообщение — и формирующаяся, и закрытая свеча. Цена (_last_price) обновляется всегда, даже на неполной свече.
  Вся логика ниже — только для закрытых баров. Только закрытие ripple-бара (15m) реально запускает пересчёт (_evaluate) — закрытия tide/wave просто обновляют скользящие окна, но сами по себе решение не триггерят.
                                                                   
  Важно: стратегия сама ордера не выставляет. Это подтверждает
  докстринг: sizing, order type and protection are downstream
  concerns — она только эмитит Signal (ENTRY/EXIT/HOLD) через
  services.emit(), который в движке публикует его в Redis-канал
  agent:events. Что дальше исполняет ордер — отдельный (видимо, ещё
  не реализованный или отдельный) компонент.

## Обновление 2026-09-17: двухэтапный пайплайн символов + масштабируемый таймаут START

### Проблема

Запуск стратегии с полным списком символов (~130 шт., выбранных на странице
Working Symbols) стабильно проваливался: `start` падал с `timed out after
20.0s`. Причина — WebSocket-подписка на потоки идёт строго последовательно
(~500мс на сообщение `SUBSCRIBE`), а на каждый символ нужно 3 подписки
(tide/wave/ripple). При 130 символах это ~195 секунд только на подписки —
далеко за фиксированным 20-секундным бюджетом команды `start`
(`COMMAND_IO_TIMEOUT_SECONDS`).

### Решение: разбить работу стратегии на 2 этапа

**Этап 1 — скрининг (`_screen_universe`, только REST, без стримов).**
По каждому символу из исходного списка (universe) тянется 1000 H4-свечей;
считаются EMA13 и EMA34 по close. Символ проходит фильтр, если **обе** EMA
растут (текущее значение выше предыдущего — тот же критерий сравнения, что
уже использовался в экране Tide для `mid_rising`/`slow_rising`). Загрузки REST
идут с ограниченной конкурентностью (`rest_concurrency`, 3–5 одновременно) —
это первое реальное использование параметра, который раньше был объявлен в
схеме настроек, но нигде не применялся.

Прошедшие фильтр ранжируются по силе тренда — относительному спреду
`(EMA13 − EMA34) / EMA34` (по убыванию). Из них отбирается не более `ws_top_n`
символов (тоже ранее не используемый параметр; переименовал дефолт 50 → 30 по
решению в этой сессии). Символ с уже открытой позицией всегда остаётся в
работе, даже если перестал проходить фильтр или выпал из топа по рангу —
до закрытия позиции.

Скрининг выполняется **на старте** стратегии и повторно **на каждой границе
H4** (с буфером 5 секунд, чтобы биржевая свеча гарантированно закрылась и была
доступна через REST) — полный список пересматривается заново каждый раз, не
только уже активные символы.

**Этап 2 — полный движок (`_apply_selection`, без изменений в самой логике
Tide/Wave/Ripple).** Только отобранный на этапе 1 набор символов получает
WS-подписки и полный REST-бэкфилл (tide/wave/ripple, окно 1000 каждый) —
именно так, как раньше делалось для *всех* символов сразу. При каждом
пересмотре набор сравнивается с текущим: новые символы подключаются, выбывшие
(без открытой позиции) — отписываются от потоков (`MarketDataStreams.
unsubscribe_kline` — новый точечный метод, раньше можно было только отписать
всё сразу через `stop()`), их локальное состояние (свечи, ожидания, cooldown,
consumed epochs) вычищается.

### Масштабируемый таймаут `start`

Раз стадия 1 линейно растёт с размером всего списка символов, а стадия 2
теперь ограничена `ws_top_n` независимо от того, сколько символов подали на
вход — таймаут команды `start` (`agent/agent/common/commands.py`) стал
зависеть от `len(symbols)`:

```
timeout = min(20.0 + 0.5 × len(symbols), 100.0)  # секунд
```

100 секунд — предел с запасом под то, что фронтенд и так уже готов ждать
результат `start` до 120 секунд (поллинг `useCommandTracking`). Остальные
команды (`stop`, `prices`, `balance`) таймаут не меняли — они не масштабируются
с числом символов.

### Отладочное логирование

По тому же плану добавлено `logger.debug` (уровень включается `LOG_LEVEL=DEBUG`
в `.env`, работает одинаково на testnet и live — стратегия не знает, на какой
сети работает):
- на каждый экран Tide при полной оценке (`_decide`) — bullish/bearish/neutral,
  все 5 условий, значения EMA;
- на каждое финальное решение (ENTRY/HOLD + reason, wave, ripple, состояние);
- на каждую проверку скрининга по символу (`rising`, значения EMA13/EMA34);
- сводка по каждому циклу скрининга (universe/qualifiers/kept_for_position/
  admitted/selected) и по каждому применению набора (added/removed/total).

### Проверено вживую

На testnet, список из 8 символов (BTCUSDT, ETHUSDT, BNBUSDT, SOLUSDT, XRPUSDT,
ADAUSDT, DOGEUSDT, LTCUSDT): скрининг прошли 3 (BNBUSDT, LTCUSDT, SOLUSDT) —
именно на них подключились WS-потоки, остальные 5 не тронуты. `start`
завершился за ~10 секунд с `ok=true`.

### Изменённые файлы

- `agent/agent/strategies/tripple_screen/strategy.py` — скрининг, применение
  набора, ре-скрининг по таймеру, точечная отписка/бутстрап.

- `agent/agent/common/commands.py` — масштабируемый таймаут `start`.
- `agent/tests/test_strategy_runtime.py`,
  `agent/tests/test_commands_lifecycle.py`,
  `agent/tests/test_engine_lifecycle.py` — тесты на новую логику и правки
  существующих под новый порядок этапов.

Формальный документ стратегии (`docs/STRATEGY_TRIPPLE_SCREEN.md`, §1.2/§9/§10)

## bootstrap, отображение отскриненных символов, отдельный лог сигналов

Живая проверка двухэтапного пайплайна на полном списке (~135 символов, live)

(`Strategy.active_symbols` → `Engine.publish_heartbeat` → `AgentHeartbeat` →
`TradingStatusView`), сразу видимый, без сворачивания.

**Отдельный лог сигналов.** Раз ENTRY/EXIT могут не появляться подолгу,
завязываться на общий (шумный, вращаемый) поток логов ненадёжно. Добавлен

ENTRY/EXIT (не HOLD), **до** публикации в Redis (запись переживёт даже сбой
`agent:events`). Файл лежит на именованном docker-volume
(`agent-signal-log:/app/agent/logs`) — переживает пересборку/пересоздание
контейнера (не переживёт только явный `docker compose down -v`).

стратегии в тестах возвращал авто-сгенерированный дочерний `Mock`, который не
